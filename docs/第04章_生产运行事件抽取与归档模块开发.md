# 第4章 生产运行事件抽取与归档模块开发

[文档导航](README.md) · [上一章](第03章_调度交接班记录模块开发.md) · [下一章](第05章_异常分级与维检工单模块开发.md)

本章先列出`operation_event`的完整目录、全部类和函数索引，再讲事件治理；调查相关文件的完整模型、工具、编排和重试说明见第5章。事件抽取不是RAG文档入库，不会自动写入ES、Qdrant或Neo4j。

## 4.1 本章目标

```text
选择交接班转写、人工运行记录或临时文本
  -> 固化来源及来源版本
  -> 创建事件抽取任务
  -> 通过统一文字模型 Provider 抽取候选事件
  -> 保存事件、事件版本和证据链接
  -> 人工修改、确认或驳回
  -> 根据需要重新抽取、合并或拆分
  -> 输出已确认生产事件
  -> 交给第5章进行异常分级和维检处置
```

事件抽取不是摘要。每个候选事件都有独立标题、事件类型、严重度、描述、置信度和来源证据。模型输出只形成`candidate`，人工确认后才成为`confirmed`事件。已确认事件是第5章异常分级Agent和维检工单流程的输入。

**本节文件：** 先通读`app/modules/operation_event/`，再对照`app/ports/models.py`和`app/ports/text.py`理解结构化输出与文字模型边界；评估Agent留到第5章介绍。

### 4.1.1 事件抽取为什么不是智能体

本章使用一次结构化模型调用，把来源正文转换为`EventCandidateList`，步骤和输出Schema均由业务代码预先确定。它没有动态工具选择、循环观察或自主终止，因此属于结构化AI抽取，不是ReAct Agent或多智能体。

| 概念 | 作用 |
|---|---|
| 候选事件 | 模型抽取但尚未被人工确认的事件 |
| 来源证据 | 记录事件来自哪段转写、人工记录或已固化的临时文字 |
| 事件版本 | 保存历次描述、扩展结构化数据和来源；标题、类型、严重度保存在主记录 |
| 合并 | 把同组织的多个候选或已确认事件归并为新候选，在新版本中保存原事件ID |
| 拆分 | 把一个混合候选拆成多个独立事件，并保留来源追溯 |
| 归档 | 人工确认后形成可供第五章分类分级使用的正式事件 |

第四章先形成稳定、可审核的事件档案，第五章才对已确认事件启动多智能体调查，避免智能体直接在未经确认的抽取结果上执行高风险判断。

## 4.3 设计数据模型

`domain/models.py`中已有以下实体：

| 实体 | 主要用途 |
|---|---|
| `ProductionEvent` | 保存稳定事件标识、主要检索字段、业务状态和当前版本指针 |
| `ProductionEventVersion` | 保存AI抽取、人工修改或合并产生的不可覆盖版本 |
| `EventSourceLink` | 保存事件与转写、人工记录或原事件之间的证据关系 |

所有实体都继承`UUIDPrimaryKeyMixin`和`TimestampMixin`，因此默认具有`id`、`created_at`和`updated_at`。

### 4.3.1 `ProductionEvent`：生产事件主记录

对应数据表`production_events`，保存事件当前对外展示的标题、类型、严重度、发生时间和生命周期状态。

| 列 | 类型 | 是否可空 | 含义 |
|---|---|---|---|
| `organization_unit_id` | UUID | 否 | 事件所属组织单元ID，用于数据范围隔离 |
| `title` | string(300) | 否 | 事件当前标题 |
| `event_type` | string(80) | 否 | 事件类型，同时建立索引便于筛选 |
| `severity` | string(20) | 否 | 严重度，接口目前允许`low`、`medium`、`high`、`critical` |
| `occurred_at` | datetime | 是 | 事件发生时间；模型只返回无法可靠解析的原文时间时可为空 |
| `business_status` | string(32) | 否 | 业务状态，如`candidate`、`confirmed`、`rejected`或`superseded` |
| `current_version_id` | UUID | 是 | 当前生效的事件版本ID |
| `created_by` | UUID | 否 | 创建事件的用户ID；AI候选使用任务创建人 |
| `confirmed_by` | UUID | 是 | 确认事件的用户ID；尚未确认时为空 |

表上按组织与发生时间、状态与更新时间建立联合索引，用于事件列表和后续归档查询。

### 4.3.2 `ProductionEventVersion`：生产事件版本

对应数据表`production_event_versions`，保存事件描述和扩展结构化数据。人工修改为原事件追加版本；合并创建新事件及其第1个版本，不覆盖原事件版本。标题、类型、严重度和发生时间只更新主记录，历史版本接口不能完整还原这些字段的旧值。

| 列 | 类型 | 是否可空 | 含义 |
|---|---|---|---|
| `event_id` | UUID | 否 | 所属生产事件ID，关联`production_events.id` |
| `version` | integer | 否 | 事件内递增的版本号，从1开始；与`event_id`组成唯一约束 |
| `source` | string(32) | 否 | 版本来源；当前使用`ai`、`manual`或`merge` |
| `description` | text | 否 | 该版本的完整事件描述 |
| `structured_data` | JSON | 否 | 扩展结构化信息；AI版本当前保存`occurred_at_text`，合并版本保存原事件ID |
| `confidence` | float | 是 | 模型抽取置信度；人工修改或合并版本可为空 |
| `created_by` | UUID | 否 | 创建该版本的用户ID |

### 4.3.3 `EventSourceLink`：事件来源证据

对应数据表`event_source_links`，把事件追溯到确切来源对象和来源版本。

| 列 | 类型 | 是否可空 | 含义 |
|---|---|---|---|
| `event_id` | UUID | 否 | 使用该证据的生产事件ID |
| `source_type` | string(60) | 否 | 来源类型，如`audio_transcript`、`manual_operation`或`production_event` |
| `source_id` | UUID | 否 | 来源主记录ID，例如录音、人工运行记录或被拆分事件ID |
| `source_version_id` | UUID | 是 | 抽取时采用的不可变来源版本ID |
| `evidence_text` | text | 是 | 模型返回或拆分过程生成的证据文字 |
| `evidence_locator` | JSON | 否 | 证据定位扩展信息；当前默认保存空对象 |

`event_id`、`source_type`和`source_id`组成唯一约束，避免同一事件重复关联同一来源主记录。

## 4.4 定义请求与响应模型

`domain/schemas.py`中的模型用于校验事件接口请求和组织事件响应，不直接对应数据库表。模型Provider的输出结构定义在`app/ports/models.py`。

### 4.4.1 `EventExtractionCreate`：创建事件抽取请求

用于选择抽取来源。数据库来源读取不可变版本；临时文字会先落为人工运行记录及版本，再创建任务。

| 属性 | 类型 | 是否必填 | 作用 |
|---|---|---|---|
| `source_type` | string | 是 | 来源类型，只允许`audio_transcript`、`manual_operation`或`raw_text` |

## 4.5 实现Repository

`OperationEventRepository`只负责生产事件的持久化查询，不调用模型，也不判断权限。

### 4.5.1 `OperationEventRepository.__init__()`

- **功能：** 保存当前异步数据库会话，供Repository方法复用。
- **重要参数：** `session`是`AsyncSession`。
- **返回：** Repository实例。

### 4.5.2 `get_event()`

- **功能：** 根据事件ID查询`ProductionEvent`。
- **重要参数：** `event_id`是生产事件UUID。
- **返回：** `ProductionEvent | None`；不存在时返回`None`，由Service决定转换成何种业务错误。

列表查询、版本查询和数据范围过滤目前仍直接写在Router中。单条事件由Service查询后，Router或Service再调用`require_data_scope()`完成对象级权限校验。

## 4.6 Service层方法详解

Service层负责来源固化、抽取任务创建、Provider调用、事件版本管理、状态转换以及合并拆分。确认、驳回和重新抽取的HTTP编排目前位于Router，本节在最后单独说明。

### 4.6.1 查询与来源处理

#### `get_event()`

- **功能：** 按ID查询生产事件；不存在时抛出`NotFoundError`。
- **重要参数：** `session`、`event_id`。
- **返回：** `ProductionEvent`。该方法不执行数据范围校验，调用者仍需根据具体操作检查权限。

#### `_source_text()`

- **功能：** 根据抽取请求解析并固化来源文字。`raw_text`会先创建一条已确认的人工运行记录及其首个版本；`audio_transcript`加载指定转写版本并检查录音数据范围；`manual_operation`加载指定或当前人工记录版本。
- **重要参数：** `payload`描述来源；`user`用于确定临时文本所属组织和校验`EVENT_EXTRACT`权限。
- **返回：** `tuple[str, UUID, UUID, str]`，依次为来源正文、来源主记录ID、来源版本ID、持久化后的来源类型。
- **关键规则：** `raw_text`最终按`manual_operation`来源处理；转写来源以`source_version_id`为准；人工记录来源验证主记录数据范围，并确认指定版本的`record_id`属于该主记录。来源状态尚未统一要求为已确认。

#### `load_persisted_source()`

- **功能：** Worker根据任务快照重新加载不可变来源正文。`audio_transcript`读取转写版本，其他来源读取人工运行记录版本。
- **重要参数：** `source_type`、`source_version_id`。
- **返回：** 来源正文字符串；版本不存在时抛出`NotFoundError`。

### 4.6.2 候选事件保存与抽取

#### `_persist_candidate()`

- **功能：** 把单个`EventCandidate`保存为一条`ProductionEvent`、第1个AI版本和可选的来源证据链接。
- **重要参数：** `candidate`是模型候选；`user`决定组织和创建人；`source_type`、`source_id`、`source_version_id`记录证据来源。
- **返回：** 新创建的`ProductionEvent`。
- **关键规则：** 初始状态为`candidate`；`occurred_at`当前固定为空，原始时间表达保存到版本的`structured_data.occurred_at_text`；方法只`flush`，不提交事务。

#### `extract_events()`

- **功能：** 解析来源并创建`event_extraction` Job，将来源类型和版本ID写入配置快照。异步模式投递到`ai_text`队列；内联模式立即调用`execute_event_extraction()`。
- **重要参数：** `payload`、`user`、文字模型`provider`、控制执行方式的`inline`。
- **返回：** `tuple[UUID, list[ProductionEvent]]`。第一项是Job ID；异步模式事件列表为空，内联模式返回本次创建的候选事件。
- **关键规则：** Job的`resource_id`保存来源主记录ID，任务快照固定来源版本，避免排队期间来源当前版本发生变化。

#### `execute_event_extraction()`

- **功能：** 执行持久化抽取任务。方法检查终态和取消请求，把Job更新为`running`，按快照选择文字Provider，调用`generate_structured(..., response_model=EventCandidateList)`，逐项保存候选事件，最后把Job更新为`succeeded`并提交。
- **重要参数：** `job`、来源`text`、`source_type`、`source_id`、`source_version_id`、`user`和默认文字模型`provider`。
- **返回：** `list[ProductionEvent]`；终态重投或任务已取消时返回空列表。
- **关键规则：** Pydantic保证模型输出结构和置信度范围合法；当前实现没有额外校验`evidence_text`必须能在原文中定位，也没有在调用Provider前单独提交`running`状态。

### 4.6.3 人工修改事件

#### `update_event()`

- **功能：** 创建新的`source=manual`事件版本，并同步更新主记录的标题、类型、严重度、发生时间和当前版本指针。
- **重要参数：** `event`、`payload`、`user`；用户需要目标事件数据范围内的`EVENT_EDIT`权限。
- **返回：** 新创建的`ProductionEventVersion`。
- **关键规则：** `rejected`和`superseded`事件不可编辑；版本号取当前最大值加一；旧版本保留。当前方法没有先对事件主记录加行锁，并发修改最终由版本唯一约束兜底；已确认事件修改后仍保持`confirmed`，不会自动重新进入候选审核。

### 4.6.4 事件合并与拆分

#### `merge_events()`

- **功能：** 把多个事件合并成一个新的候选事件，并把原事件标记为`superseded`。新事件类型沿用第一个事件，严重度取最高值，发生时间取已有时间中的最早值。
- **重要参数：** `payload.event_ids`至少两个事件ID，`payload.title`是合并后标题；`user`需要每个事件数据范围内的`EVENT_TRANSFORM`权限。
- **返回：** 新创建的`ProductionEvent`。
- **关键规则：** 仅`candidate`或`confirmed`事件可合并，且必须属于同一组织；新版本`source=merge`，描述由原事件标题拼接，`structured_data`保存原事件ID。当前实现没有把原事件的`EventSourceLink`复制给新事件，追溯需先读取`merged_event_ids`再查询原事件。请求仅约束列表长度，没有校验ID互不重复。

#### `split_event()`

- **功能：** 根据请求中的多个条目创建新的候选事件，并把原事件标记为`superseded`。每条新事件通过`production_event`类型的来源链接指向原事件及其当前版本。
- **重要参数：** `event`、至少包含两个`SplitEventItem`的`payload`、需要`EVENT_TRANSFORM`权限的`user`。
- **返回：** `list[ProductionEvent]`，包含所有拆分后事件。
- **关键规则：** 仅`candidate`或`confirmed`事件可拆分；拆分项通过`EventCandidate`复用候选保存逻辑，置信度固定为1.0，证据文本记录原事件ID。新事件不会直接复制原事件更早的来源链接，而是通过原事件形成间接追溯。虽然由人工提交拆分条目，当前复用`_persist_candidate()`，所以新版本的`source`仍为`ai`，不是独立的`split`来源；不要把这个值理解为拆分时再次调用了模型。

### 4.6.5 Service之外的审核与重新抽取

以下业务目前由`api/router.py`直接编排，不是Service方法：

- `confirm_event()`只允许把`candidate`改为`confirmed`，记录`confirmed_by`和审计日志。
- `reject_event()`只允许驳回`candidate`，把状态改为`rejected`，并把`reason`写入审计日志。
- `reextract_event()`读取事件当前版本的描述，以`raw_text`方式重新创建抽取任务；这会先生成一条新的人工运行记录作为来源，不会修改或删除原事件。
- 事件列表、详情和版本历史查询也由Router直接执行，其中列表查询使用`data_scope_clause()`在SQL层过滤组织范围。

## 4.7 Task后台任务入口详解

`application/tasks.py`是Celery Worker与Service的适配层。本章只介绍事件抽取Task；同一文件中的分类分级Task属于第5章业务流程，在下一章统一说明。

```text
AsyncJob 和 TaskOutbox
  -> Celery Task 接收 job_id
  -> _extract() 加载 Worker 资源
  -> 根据 Job 快照恢复来源版本
  -> Service execute_event_extraction() 执行业务
  -> 返回 Job 最终状态
```

### 4.7.1 `_extract()`：执行事件抽取后台任务

- **功能：** 加载Job，从配置快照读取来源类型和来源版本，重新加载持久化来源正文，恢复任务用户并调用`execute_event_extraction()`。
- **重要参数：** `job_id`是字符串形式的Job UUID。
- **返回：** `str`类型的Job最终状态。
- **异常处理：** 任一步骤异常都会调用`mark_job_failed()`记录失败信息，然后重新抛出供Celery感知。

### 4.7.2 `extract_events_task()`：Celery抽取入口

- **功能：** 注册名为`app.modules.operation_event.extract_events`的同步Celery任务，通过`asyncio.run()`调用异步`_extract()`。
- **重要参数：** `job_id`，由Outbox发布器传入。
- **返回：** `dict[str, str]`，包含`job_id`和最终`status`。
- **关键配置：** `acks_late=True`，执行完成后才确认消息；已提交终态的消息重投会直接返回。抽取执行器没有分类任务的独占租约，并发重复投递仍可能在终态提交前分别进入模型调用，不能据此宣称严格幂等。

## 4.8 注册API

生产事件模块提供：

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/api/v1/event-extractions` | 从转写、人工记录或临时文字创建事件抽取任务 |
| GET | `/api/v1/events` | 按当前用户数据范围查询最近100条事件 |
| GET | `/api/v1/events/{event_id}` | 查询事件主记录 |
| GET | `/api/v1/events/{event_id}/versions` | 查询事件全部历史版本 |
| PUT | `/api/v1/events/{event_id}` | 人工修改事件并创建新版本 |
| POST | `/api/v1/events/{event_id}:confirm` | 确认候选事件 |
| POST | `/api/v1/events/{event_id}:reject` | 驳回候选事件并记录原因 |
| POST | `/api/v1/events/{event_id}:reextract` | 基于事件当前描述重新创建抽取任务 |
| POST | `/api/v1/events:merge` | 合并多个事件并将原事件标记为已取代 |
| POST | `/api/v1/events/{event_id}:split` | 拆分事件并将原事件标记为已取代 |

抽取接口返回202。内联模式会在响应中同时返回本次生成的事件ID；真实异步模式只立即返回Job ID，客户端通过统一Job查询能力获取进度。列表接口在SQL层执行数据范围过滤，单条事件和版本历史查询在读取事件后执行对象级校验。

`POST /api/v1/events/{event_id}:classify`虽然注册在`operation_event/api/router.py`，但它启动的是第5章异常分级、人工审核和维检工单流程，因此放在下一章介绍。

## 4.9 与调查、知识和报告的衔接

| 当前操作 | 保存的事实 | 下一步 |
|---|---|---|
| 事件抽取 | 来源主记录及固定版本、候选事件与证据链接 | 人工确认，不自动启动调查 |
| 人工修改/合并/拆分 | 新版本；合并/拆分会取代原事件 | 合并/拆分的新候选需确认，人工修改不自动撤销已有确认 |
| `:classify` | 固定事件版本的Job与AgentRun | 第5章调查、审核和工单 |
| 报告汇集 | 已确认事件当前版本的来源快照 | 第7章报告草稿 |
| 导入知识资料 | 需要独立知识文档与版本 | 第8章；当前没有自动事件表同步连接器 |

`job_user()`在Worker中重新读取当前授权。事件抽取本身仍使用终态与业务校验，不要把分类任务已接入的租约机制泛化到所有事件任务。

## 4.10 验证顺序

使用已授权账号创建抽取任务，检查候选不能直接分类；修改后检查新版本，确认后再进入第5章。合并与拆分需要验证旧事件被取代及来源可追溯。

异步模式需要`ai_text`和`maintenance`消费者以及Beat。配置独立测试库后执行：

```bash
uv run pytest tests/test_event_and_work_order_flow.py tests/test_authorization.py tests/test_contract.py --tb=short
```

验证状态机和权限，不仅检查HTTP 202。不要把结构化字段合法理解成事件事实已经由模型证明正确。
