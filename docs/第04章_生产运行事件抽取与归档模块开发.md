# 第 4 章 生产运行事件抽取与归档模块开发

## 4.1 本章目标

本章把交接班转写、人工运行记录等文字来源转换为可审核、可追溯的生产事件。完整流程如下：

```text
选择来源及来源版本
  -> 创建事件抽取 Job
  -> 千问返回严格结构化候选事件
  -> 保存事件、事件版本和证据链接
  -> 人工修改、确认或驳回
  -> 必要时重新抽取、合并或拆分
  -> 已确认事件进入分类分级和报告数据集
```

事件抽取不是简单摘要。每个事件必须拥有独立标题、类型、严重度、描述、证据文本和来源版本。

## 4.3 设计事件实体

建立三类核心实体：

| 实体 | 职责 |
|---|---|
| `ProductionEvent` | 稳定事件标识、当前版本和业务状态 |
| `ProductionEventVersion` | 描述、结构化数据、置信度和来源方式 |
| `EventSourceLink` | 事件版本与原始记录版本之间的证据关系 |

主记录与版本分离可以同时满足：

- 事件 ID 在生命周期中保持稳定；
- 人工修改不覆盖模型输出；
- 报告能够引用当时采用的事件版本；
- 重新抽取、合并和拆分均可审计。

关键字段示例：

```python
class ProductionEvent(UUIDPrimaryKeyMixin, TimestampMixin, Base):
    __tablename__ = "production_events"

    organization_unit_id: Mapped[UUID]
    title: Mapped[str]
    event_type: Mapped[str]
    severity: Mapped[str]
    occurred_at: Mapped[datetime | None]
    business_status: Mapped[str]
    current_version_id: Mapped[UUID | None]
    created_by: Mapped[UUID]
    confirmed_by: Mapped[UUID | None]
```

候选事件的初始状态为 `candidate`。正式报告和工单流程只能使用 `confirmed` 事件。

## 4.4 定义结构化输出

在 `app/ports/models.py` 中建立严格模型：

```python
class EventCandidate(StrictProviderOutput):
    title: str
    event_type: str
    occurred_at_text: str | None
    description: str
    severity: str
    confidence: float = Field(ge=0, le=1)
    evidence_text: str


class EventCandidateList(StrictProviderOutput):
    events: list[EventCandidate]
```

`extra="forbid"` 用于拒绝未定义字段。`evidence_text` 必须是输入来源中的原文片段，不能是模型解释。

## 4.5 定义抽取请求

```python
class EventExtractionCreate(BaseModel):
    source_type: str = Field(pattern=r"^(audio_transcript|manual_operation|raw_text)$")
    source_id: UUID | None = None
    source_version_id: UUID | None = None
    raw_text: str | None = None
```

`audio_transcript` 和 `manual_operation` 从数据库加载权威版本；`raw_text` 会先保存为一条已确认的人工运行记录及其版本，再进入抽取流程。这样不会让一次性文本脱离来源和版本管理。

支持的来源类型至少包括：

- `audio_transcript`；
- `manual_operation`；
- `raw_text`。

## 4.6 创建抽取任务

`POST /event-extractions` 执行：

1. 验证来源存在且属于用户数据范围；
2. 读取不可变的来源版本；
3. 创建 `ai_jobs`，类型为 `event_extraction`；
4. 保存来源类型、ID、版本 ID 和摘要哈希到 `config_snapshot`；
5. 创建 `task_outbox`，队列为 `ai_text`；
6. 返回 202 和 Job ID。

来源版本必须进入任务快照。否则来源后来被人工修改时，无法证明模型当时处理的是哪段文本。

## 4.7 调用千问抽取事件

Service 通过 `TextLLMProvider` 调用：

```python
result = await provider.generate_structured(
    operation="event_extraction",
    system_prompt=(
        "你是油气管网生产运行事件抽取助手。只抽取输入文字明确出现的事件。"
        "不得补造时间、设备状态、原因或处理结果。evidence_text 必须来自原文。"
    ),
    user_prompt=raw_text,
    response_model=EventCandidateList,
)
```

抽取后还要执行确定性校验：

- `evidence_text` 能在规范化后的来源文本中定位；
- `severity` 位于项目允许枚举；
- 标题和描述非空；
- 置信度在 0 到 1 之间；
- 同一 Job 内不存在内容完全相同的候选；
- `occurred_at_text` 不能解析时保留原文字段，`occurred_at` 设为空。

模型输出通过 Pydantic 只表示结构合法，不表示业务事实已经确认。

## 4.8 保存事件和证据

每个候选项创建：

1. 一条 `ProductionEvent`；
2. 一条 `ProductionEventVersion`，`source=model`；
3. 一条 `EventSourceLink`，保存来源对象、来源版本和证据文本；
4. 一条审计日志。

保存完成后更新 Job 为 `succeeded`。如果一个候选项不合法，应使整次任务失败或采用明确的逐项拒绝策略，不能静默丢弃而不记录原因。

## 4.9 人工修改、确认和驳回

人工修改通过 `PUT /events/{event_id}` 创建新版本：

```python
class EventUpdate(BaseModel):
    title: str
    event_type: str
    severity: str
    occurred_at: datetime | None
    description: str
    structured_data: dict = Field(default_factory=dict)
```

确认前检查：

- 当前版本存在；
- 事件至少有一条有效来源链接；
- 类型和严重度符合业务配置；
- 用户具备 `event:confirm` 权限；
- 用户组织范围覆盖事件组织。

确认后 `business_status=confirmed`，记录 `confirmed_by`。驳回时 `business_status=rejected`，并在审计日志中保存原因。

## 4.10 重新抽取

`POST /events/{event_id}:reextract` 创建新 Job，不删除原事件。重新抽取结果创建新的候选事件或新版本，并记录父任务 ID。这样可以比较提示词版本或模型版本之间的结果差异。

## 4.11 合并事件

合并适用于多条候选记录描述同一业务事实的情况。请求：

```python
class MergeEventsInput(BaseModel):
    event_ids: list[UUID] = Field(min_length=2)
    title: str = Field(min_length=2, max_length=300)
```

Service 必须校验：

- 所有事件属于同一组织范围；
- 事件未被其他合并操作标记为 `superseded`；
- 来源链接不会丢失；
- 合并后的新事件建立新版本；
- 原事件设为 `superseded`，不物理删除。

## 4.12 拆分事件

拆分用于一条候选记录包含多个独立业务事实的情况：

```python
class SplitEventItem(BaseModel):
    title: str
    event_type: str
    severity: str
    description: str


class SplitEventInput(BaseModel):
    items: list[SplitEventItem] = Field(min_length=2)
```

每个新事件继承原来源链接，同时形成独立版本；原事件设为 `superseded`。

## 4.13 分类分级入口

`POST /events/{event_id}:classify` 只允许已确认事件调用。任务类型为 `event_classification`，队列为 `maintenance`。

结构化输出：

```python
class AssessmentCandidate(StrictProviderOutput):
    category: str
    risk_level: str
    rationale: str
    recommended_action: str
```

结果保存到 `abnormality_assessments`，状态为 `pending`，同时创建 `workflow_runs`，状态为 `awaiting_review`。本接口只产生审核候选，不直接创建维检工单。

## 4.14 注册 API

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/api/v1/event-extractions` | 创建抽取任务 |
| GET | `/api/v1/events` | 按组织、状态、类型筛选事件 |
| GET | `/api/v1/events/{id}` | 查询事件 |
| GET | `/api/v1/events/{id}/versions` | 查询版本历史 |

| POST | `/api/v1/events/{id}:reject` | 驳回事件 |

| POST | `/api/v1/events/{id}:split` | 拆分事件 |
| POST | `/api/v1/events/{id}:classify` | 创建分类分级任务 |

- 拆分后来源链接保留；
- 未确认事件不能分类；

## 4.16 手工联调顺序

1. 取得一条交接班转写版本或人工运行记录版本；
2. 调用 `POST /event-extractions`；
3. 查询 Job 直到完成；
4. 查询候选事件和来源链接；
5. 修改其中一条事件；
6. 查看版本历史；
7. 确认事件；
8. 调用分类接口并记录 Workflow ID。
