# 第2章 公共基座搭建、启动与测试

[文档导航](README.md) · [上一章：项目技术与功能模块](第01章_项目技术与功能模块介绍.md) · [下一章：调度交接班](第03章_调度交接班记录模块开发.md)

## 2.1 公共基座的范围

公共基座是所有业务模块共同依赖的部分。它不处理某一种具体业务，而是统一提供配置、数据库、认证授权、文件存储、模型访问、异步任务、幂等、审计、错误处理和应用装配。先建立这些能力，再开发交接班、事件、工单等业务模块，可以避免每个模块各写一套连接、权限和任务代码。

本章按照适合实际开发的顺序介绍文件。这里的顺序不是Python强制要求，而是为了让每一步都建立在前一步已经明确的契约上。阅读现有项目时也可以沿着这个顺序理解。

## 2.2 建立项目和配置入口

第一步编写`pyproject.toml`，确定Python版本、运行依赖、开发依赖、构建方式以及Pytest、Ruff、Mypy和Coverage配置。随后生成并提交`uv.lock`，让本地、CI和镜像使用同一套依赖版本。

第二步编写`.env.example`和`app/bootstrap/config.py`。环境示例负责列出部署时需要提供的参数，`Settings`负责读取、转换和校验这些参数。数据库、JWT、Celery、模型、存储和知识服务都应从同一个配置对象取得参数，业务模块不应各自读取环境变量。

第三步编写`app/__init__.py`，保存应用版本等最小包信息。版本可以进入健康检查、OpenAPI和发布制品，便于确认当前运行的是哪一版代码。

## 2.3 建立数据库公共层

先编写`app/shared/db.py`，创建异步SQLAlchemy Engine、Session Factory和事务生命周期。所有业务模块都从这里获得数据库会话，避免重复创建连接池。

然后编写`app/shared/model_mixins.py`和`app/shared/ids.py`。Mixins统一主键、创建时间和更新时间等公共字段，ID辅助函数统一标识生成方式。再编写`app/shared/types.py`，集中放置多个模块都会使用的枚举或值类型。

接下来建立`alembic.ini`、`alembic/env.py`和迁移版本文件。迁移环境需要导入全部ORM模型的Metadata，才能创建完整Schema。当前项目使用`alembic/versions/20260926_0001_initial_schema.py`作为初始基线。

最后编写`scripts/verify_postgres_schema.py`。迁移成功只能说明脚本执行完毕，Schema校验还要确认表、索引、约束和Alembic版本是否符合当前模型。

## 2.4 建立统一错误和请求上下文

编写`app/shared/errors.py`，定义稳定的业务错误码、HTTP状态和统一响应结构。应用服务抛出业务异常，API层由统一处理器转换响应，避免每个接口重复拼装错误JSON。

随后编写`app/shared/security/audit/context.py`，保存当前请求编号等审计上下文。`app/main.py`中的中间件读取或生成`X-Request-ID`，将其写回响应，并让后续日志和审计记录能够关联同一次请求。

## 2.5 建立认证、授权和审计

先编写`app/shared/security/authentication/schemas.py`和`dependencies.py`，完成Bearer Token提取、JWT签名验证、issuer、audience和有效期检查。开发环境的签发服务位于`dev/mock_idp`，正式环境应接入外部IdP。

然后编写`app/shared/security/identity/models.py`、`schemas.py`和`repository.py`，用`issuer + subject`把外部身份映射为本地用户。后端不能只相信JWT里附带的角色，而要重新读取数据库中的用户状态和授权。

再编写`app/shared/security/authorization/permissions.py`、`models.py`、`scopes.py`、`repository.py`和`dependencies.py`。这些文件依次定义权限码、角色与授权数据、组织范围判断、授权查询以及FastAPI权限依赖。

最后编写`app/shared/security/router.py`和`authorization/router.py`，提供当前用户、组织、用户、角色、角色分配、有效权限和审计日志接口。初始化管理员和内置角色的脚本分别位于`scripts/bootstrap_security.py`与`scripts/bootstrap_mock_idp_users.py`。

## 2.6 建立模型和存储端口

先编写`app/ports/text.py`、`speech.py`、`vision.py`和`storage.py`，定义业务层可以调用的方法、输入和输出。端口只描述能力，不包含某个供应商的HTTP地址、SDK对象或认证方式。

然后在`app/infrastructure/providers`中实现千问、OpenAI兼容接口、本地HTTP、自建HTTP和Fake Provider，在`app/infrastructure/storage`中实现本地文件系统、内存和S3适配器。

接着编写`app/bootstrap/providers.py`和`model_registry.py`。前者根据配置选择适配器并组成Provider Bundle，后者集中维护模型能力与别名。业务模块只依赖端口，启动层负责选择实际实现。

## 2.7 建立文件和媒体公共层

依次编写`app/shared/media/names.py`、`integrity.py`、`documents.py`和`preview.py`。这些文件分别处理安全文件名、大小与哈希校验、文档辅助操作和图片预览。

再编写`app/shared/media/router.py`，提供受控上传和下载入口。本地文件系统使用签名地址访问私有对象，S3实现可以返回预签名URL。上传完成后仍要检查对象是否存在，并核对大小、MIME和SHA-256。

## 2.8 建立异步任务平台

先编写`app/shared/platform/models.py`和`schemas.py`，建立`AsyncJob`、执行尝试、Outbox、幂等记录和模型调用日志等公共数据结构。

然后编写`idempotency.py`，处理需要保护的重复写请求；编写`execution.py`，管理任务租约、执行令牌、心跳、取消和完成；编写`service.py`，提供创建任务、写入Outbox和记录模型调用等公共方法。

接着编写`runtime.py`和`tasks.py`。运行时维护负责处理超时任务和过期资源，公共Celery任务负责发布Outbox及执行周期维护。`capabilities.py`集中说明可观测的模型和运行能力。

再编写`app/shared/worker_runtime.py`和`app/bootstrap/job_lifecycle.py`。前者为Worker任务装配数据库、Provider和权限上下文，后者把业务重试处理器注册到公共任务生命周期中。

最后编写`app/bootstrap/celery_app.py`，注册所有任务模块、队列路由、可靠性参数和Celery Beat计划。业务模块增加异步任务后，需要在这里加入任务模块和路由。

## 2.9 建立知识资源

先完成文档解析、Embedding和Reranker服务的HTTP契约，再编写Elasticsearch、Qdrant和Neo4j适配器。三类索引各自负责全文、向量和关系检索，但正式文档状态仍由PostgreSQL保存。

然后编写`app/bootstrap/knowledge.py`，集中创建和关闭解析、Embedding、重排及三类索引资源。知识资源采用延迟建立连接的方式，但知识模块本身始终装配，不设置启停开关。

索引首次部署时可以使用`scripts/bootstrap_knowledge_indexes.py`建立需要的索引结构。服务是否就绪由`/health/knowledge`检查，API整体就绪还要通过`/health/ready`。

## 2.10 完成应用装配

最后编写`app/main.py`。应用生命周期按照配置创建数据库、Provider、知识资源和任务重试处理器，注册异常处理器、中间件、健康检查、MCP端点与全部业务路由，并在退出时依次关闭资源。

到这一步，公共基座已经具备业务模块需要的运行环境。后续模块只需要添加自己的领域模型、Schema、Repository、Application Service、Celery Task和API Router，再把路由与任务入口注册到应用装配层。

## 2.11 准备本地环境

安装Python并恢复锁定依赖：

```bash
uv python install 3.14
uv sync --frozen --group dev
```

首次配置时复制环境模板。已有`.env`时不要覆盖：

```bash
cp .env.example .env
cp infra/env/knowledge.env.example .env.knowledge
```

`.env`需要配置数据库、RabbitMQ、Redis、JWT、文字模型、ASR、视觉、存储和知识服务连接。`.env.knowledge`需要配置Elasticsearch、Qdrant、Neo4j、解析、Embedding和重排服务使用的密码、API Key与模型版本。这两个文件都不能提交真实密钥。

## 2.12 启动基础设施

共享基础设施可以按服务单独启动，也可以一次启动整组。后端正常运行至少需要PostgreSQL、RabbitMQ和Redis：

```bash
docker compose --env-file .env -f infra/compose/shared.yml up -d postgres rabbitmq redis
```

`shared.yml`还定义MySQL和SeaweedFS。MySQL目前不属于主业务数据库；SeaweedFS只在需要演练S3兼容存储时启动：

```bash
docker compose --env-file .env -f infra/compose/shared.yml up -d seaweedfs
docker compose --env-file .env -f infra/compose/project.yml --profile s3-local run --rm object-storage-init
```

知识模块是固定组成部分，需要启动完整知识栈：

```bash
docker compose --env-file .env.knowledge -f infra/compose/knowledge.yml config --quiet
docker compose --env-file .env.knowledge -f infra/compose/knowledge.yml up -d --build
```

这组命令启动文档解析、Embedding、重排、Elasticsearch、Qdrant和Neo4j。首次启动模型服务会下载权重，需要等待模型加载和健康检查完成。

使用本地语音和视觉Provider时，再启动ASR和视觉服务：

```bash
docker compose --env-file .env -f infra/compose/project.yml --profile local-models up -d --build asr vision
```

只调试不涉及录音和图片的接口时，可以暂时不调用ASR和视觉能力；知识服务不能从后端就绪检查中省略。

## 2.13 初始化数据库和开发身份

PostgreSQL容器第一次启动后，创建开发数据库和独立测试数据库。数据库已经存在时不需要重复执行：

```bash
docker exec postgres createdb -U peter pipechina
docker exec postgres createdb -U peter pipechina_test
```

确认`.env`中的`DATABASE_URL`指向开发数据库后，执行数据库迁移：

```bash
uv run alembic upgrade head
uv run python scripts/verify_postgres_schema.py
```

本地开发使用Mock IdP时，初始化开发用户和权限：

```bash
uv run python scripts/bootstrap_mock_idp_users.py
```

生产环境不使用固定开发账号，应在迁移完成后通过`scripts/bootstrap_security.py`建立第一个与真实IdP身份绑定的管理员。

## 2.14 启动后端进程

先启动本地Mock IdP。生产环境由真实IdP代替该进程：

```bash
uv run uvicorn dev.mock_idp.main:app --host 127.0.0.1 --port 9001 --reload
```

再启动FastAPI：

```bash
uv run uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

启动Celery Worker并监听项目使用的全部队列：

```bash
uv run celery -A app.bootstrap.celery_app:celery_app worker -l INFO -Q audio,ai_text,vision,report,maintenance,knowledge_index,knowledge_query,knowledge_eval
```

最后启动Celery Beat：

```bash
uv run celery -A app.bootstrap.celery_app:celery_app beat -l INFO
```

API负责接收请求，Worker负责异步任务，Beat负责周期投递，三者必须分别运行。只启动API时，可以访问同步接口，但Outbox消息、模型任务、提醒和定时清理不会被完整执行。

## 2.15 检查运行状态

查看容器状态：

```bash
docker compose --env-file .env -f infra/compose/shared.yml ps
docker compose --env-file .env.knowledge -f infra/compose/knowledge.yml ps
docker compose --env-file .env -f infra/compose/project.yml --profile local-models ps
```

检查API进程和全部固定依赖：

```bash
curl http://127.0.0.1:8000/health/live
curl http://127.0.0.1:8000/health/ready
curl http://127.0.0.1:8000/health/knowledge
```

`live`返回成功只表示API进程存活。`ready`需要PostgreSQL和所有知识组件通过检查。`knowledge`会分别报告解析、Embedding、重排、全文、向量和图组件状态。

## 2.16 准备测试数据库

测试夹具会删除测试数据库的`public` Schema并重新创建，因此必须使用独立、可丢弃的数据库。不要让`TEST_DATABASE_URL`指向开发库或任何业务库。

测试数据库建立后，在当前终端设置连接：

```bash
export TEST_DATABASE_URL=postgresql+asyncpg://peter:123456@127.0.0.1:5432/pipechina_test
```

如果没有设置`TEST_DATABASE_URL`，测试代码可能回退读取`DATABASE_URL`。执行测试前必须确认最终地址确实是测试库。

先运行不依赖真实模型的公共层测试：

```bash
uv run pytest -q \
  tests/test_architecture.py \
  tests/test_auth_and_health.py \
  tests/test_authorization.py \
  tests/test_provider_contracts.py \
  tests/test_provider_factory.py \
  tests/test_media_security.py \
  tests/test_local_filesystem_storage.py \
  tests/test_async_worker_and_outbox.py \
  tests/test_platform_hardening.py \
  tests/test_contract.py
```

MCP和多智能体公共运行边界可以单独验证：

```bash
uv run pytest -q \
  tests/test_mcp_server.py \
  tests/test_multi_agent_runtime.py \
  tests/test_agent_offline_evaluation.py
```

知识基座的Fake与数据库测试可以这样运行：

```bash
uv run pytest -q \
  tests/test_knowledge_foundation.py \
  tests/test_knowledge_business.py \
```

`tests/test_knowledge_external.py`和`tests/test_knowledge_live_models.py`面向真实外部索引或模型，需要相应服务、凭据和显式环境配置。它们被跳过不代表真实服务已经验证通过。

## 2.18 运行完整质量检查

提交前按CI顺序执行：

```bash
uv lock --check
uv run ruff format --check .
uv run ruff check .
uv run mypy app scripts dev
uv run python -m compileall -q app alembic tests scripts dev services
uv run coverage erase
uv run coverage run -m pytest -W error
uv run coverage report
uv run alembic upgrade head
uv run python scripts/verify_postgres_schema.py
uv run pip-audit --local --skip-editable
```

Ruff、Mypy、编译和依赖审计检查代码与环境质量，Pytest检查行为，Coverage检查测试触达范围，Alembic和Schema脚本检查数据库结构。任何单项通过都不能替代其他检查。

## 2.19 推荐的日常启动顺序

日常开发按以下顺序启动，出现问题时更容易定位：

1. PostgreSQL、RabbitMQ和Redis；
2. 完整知识栈；
3. 按Provider配置启动ASR、视觉或S3兼容存储；
4. 执行Alembic迁移；
5. 启动Mock IdP或确认外部IdP可用；
6. 启动FastAPI并检查`/health/ready`；
7. 启动Celery Worker；
8. 启动Celery Beat；
9. 启动前端并进行接口联调。

关闭环境时应先停止产生新任务的前端和API，再停止Beat和Worker，最后停止模型与基础设施容器。数据库、索引和对象存储的数据Volume是否保留，应根据是否需要保留开发数据决定，不能把删除容器和删除数据卷当成同一操作。
