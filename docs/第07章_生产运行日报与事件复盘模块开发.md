## 7.1 定位与代码入口

报告模块汇集已有业务来源，生成可编辑草稿，保留版本与来源快照，经人工审核后发布，支持DOCX和PDF导出。报告生成不自动检索整个知识库。

| 入口 | 作用 |
|---|---|
| [domain/models.py](../app/modules/report/domain/models.py) | OperationReport、ReportVersion、ReportSource、ReportExport |
| [domain/schemas.py](../app/modules/report/domain/schemas.py) | 创建、内容更新、审核、导出契约 |
| [application/service.py](../app/modules/report/application/service.py) | 来源汇集、生成、版本、导出 |
| [application/workflow.py](../app/modules/report/application/workflow.py) | 分组与Map-Reduce |
| [application/tasks.py](../app/modules/report/application/tasks.py) | Worker与定时日报 |
| [api/router.py](../app/modules/report/api/router.py) | API、审核发布入口 |

本章解释当前文件，不要求重新创建项目或覆盖现有模型。具体字段、长度和状态转换以这些源码为准。

## 7.2 来源范围：不是所有来源都叫“已确认”

| 来源 | 当前选择规则 | 固化内容 |
|---|---|---|
| 交接班音频 | 同组织、已确认、指定业务日、未删除，可按班次筛选 | 当前摘要等结构化信息 |
| 生产事件 | 同组织、已确认，按发生日或缺失发生时间时的创建日筛选，可按事件类型筛选 | 当前事件版本 |
| 工单 | 同组织，非关闭/取消状态，或在当日更新的终态工单 | 标题、状态、风险等；可能包含草稿 |
| 巡检 | 同组织、当天记录，可按站场/管线筛选 | 已确认隐患 |

范围字段不是对每种来源都通用：班次用于交接班，事件类型用于事件，站场/管线用于巡检。不能把某一个过滤条件写成全模块统一约束。

手工记录不是单独的直接来源通道；知识库检索也没有自动接入。报告提示词虽然要求“已确认来源”，但工单选择代码确实包含非终态草稿，使用和评审时必须注意这个差异。

来源在任务执行时汇集，不是在点击生成时就冻结所有业务数据。模型运行配置快照与业务来源快照是两件事。生成成功后保留来源快照，供追溯所采用的数据。

## 7.3 数据模型与版本

- OperationReport：组织、报告类型、业务日期、范围及其规范化摘要、状态、当前版本指针。
- ReportVersion：版本号、标题、结构化内容、来源类型等历史内容。
- ReportSource：关联生成使用的来源与快照，不依赖原业务记录永远不变化。
- ReportExport：固定导出的report_version_id、格式、任务状态及对象键。

编辑生成新版本，不原地覆盖历史。恢复历史版本通过内容更新再建一个版本，不是删除后来的版本或直接倒拨历史记录。内容变化后报告回到草稿，需要重新履行审核发布流程。

## 7.4 LangGraph与模型的真实关系

```text
来源集合 → LangGraph 分组（每组 20 条）→ 确定性统计来源 ID/数量
→ 图外依次调用文本模型生成每组草稿 → 确定性合并 → 保存新版本
```

build_report_graph() 的节点是partition、map_deterministic、reduce_deterministic。图里的map/reduce处理统计与ID，不直接调用模型。

generate_report_map_reduce() 在图运行之后依次await各分组模型调用。当前不是并行Map，也不是多Agent；LangGraph在这里是有向流程组织工具。状态持久化由项目数据库承担，不能宣称已经配置LangGraph checkpoint恢复机制。

单份草稿直接返回；多份草稿按标题聚合章节内容、去重pending_facts，并汇集来源ID。保存时只关联可识别的来源ID。这个检查不等于对每个自然语言结论做语义证明；报告仍需要人工审核。

模型接收结构化文本，不在该链路直接接收原音频或图片。实际文本模型由Provider与运行快照决定，文档不固定为某一个产品型号。

## 7.5 异步生成与状态

生成请求创建report队列任务，通过公共运行快照固化模型和提示词配置；异步时经Outbox投递。执行端检查任务状态、读取来源、生成草稿、保存版本和来源，再标记任务完成。

本模块没有全面接入RAG使用的公共执行租约。模型超时、重复投递和取消应按现有任务检查点验证，不能宣称全部操作exactly-once或即时取消。

审核与发布是独立动作，内容更新会使草稿重新进入人工流程。业务接口的权限检查、状态前置条件和版本字段以router/service为准；不要直接修改数据库状态跳过审核。

## 7.6 DOCX和PDF导出

创建导出时固定当前report_version_id，后台使用该版本生成文件。后续编辑报告不应改变已经创建的导出版本含义。

DOCX由python-docx生成，对象键为：

```text
reports/{report.id}/exports/{export.id}.docx
```

文件通过StorageProvider保存和签名下载，既可使用本地实现，也可使用S3。下载地址有时效，不是公开永久URL。

导出支持DOCX与PDF。PDF使用随应用打包的Noto Sans SC字体生成，固定报告版本并写入私有存储；两种格式都通过带时效的下载地址访问。

## 7.7 定时日报的日期语义

Celery Beat配置UTC 16:10，对应上海时区次日00:10。任务遍历启用组织，以业务日期和规范化空范围摘要检查已有记录，避免重复建立同一范围日报。

任务以`datetime.now(Asia/Shanghai).date() - timedelta(days=1)`为业务日期，在00:10汇总刚结束的前一日。跨年和跨月由日期运算处理。

定时任务内部调用inline生成流程，不是为每个组织再排一个独立生成消息。定时建单去重也不代表整个任务链具有exactly-once保证。

## 7.8 API导航

下表省略 /api/v1前缀，精确请求体见Schema。

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | /reports | 创建报告 |
| GET | /reports/{report_id} | 报告详情 |
| POST | /reports/{report_id}:generate | 生成草稿 |
| GET | /reports/{report_id}/versions | 历史版本 |
| PUT | /reports/{report_id}/content | 编辑内容 |
| POST | /reports/{report_id}/versions/{version_no}:restore | 从历史内容创建新版本 |
| POST | /reports/{report_id}:submit-review | 提交审核 |
| POST | /reports/{report_id}:review | 审核 |
| POST | /reports/{report_id}:publish | 发布 |
| POST | /reports/{report_id}:withdraw | 撤回发布 |
| POST | /reports/{report_id}/exports | 创建导出 |
| GET | /reports/{report_id}/exports/{export_id} | 导出状态与成功后的签名下载地址 |

来源快照当前在数据库中持久化；没有单独的`/sources`读取接口，不能按上层概念推断API已存在。

## 7.9 验证顺序

先按第1章启动公共环境。Worker应消费report，同时保留maintenance消费与Beat/Outbox发布，不要只启动report队列后期待所有后台链路自行运行。

准备已确认交接班、事件和隐患，以及不同状态工单；验证范围过滤→生成→来源快照→编辑→恢复→审核→发布→DOCX/PDF导出。另需检查生成期间源数据变化、未知来源ID、空来源及跨日定时触发。

先配置可丢弃的独立TEST_DATABASE_URL；测试夹具会重建public schema。确认后运行：

```bash
uv run pytest tests/test_report_flow.py tests/test_scheduled_report.py tests/test_workflows.py -q
```

这些测试验证覆盖范围内的逻辑，不证明真实模型输出质量、导出排版或生产容灾已经验收。后续知识模块见第8章；完成本章不等于全部业务模块已经验证完成。

## 7.10 部署核对

- 业务库和测试库分开，数据库与对象存储有备份恢复方案。
- 文本模型地址、凭据、超时及数据出域审批符合部署要求。
- 定时业务日期与业务部门定义一致。
- 只部署一个受控Beat调度入口，并监控任务积压与失败。
- DOCX和PDF均需验证实际下载、打开和版式。
- 发布版本、Git标签和上线操作按团队流程单独审批，不由阅读文档自动执行。
