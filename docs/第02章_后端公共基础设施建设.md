# 第 2 章 后端公共基础设施建设

## 2.1 本章目标

本章建立五个业务模块共同依赖的后端基座。这里的“基座”不是某个业务模块，而是一组稳定、可复用的能力：

- 统一读取和校验 `.env`；
- 管理异步数据库连接、ORM 基类和 Alembic 迁移；
- 统一错误响应、请求标识和 HTTP 幂等；
- 完成 JWT/OIDC 身份认证、数据库 RBAC 和数据范围控制；
- 为文字模型、语音识别、视觉模型和文件存储定义稳定端口；
- 装配可替换的 Provider；
- 管理 AI Job、事件、配置版本、审计和事务 Outbox；
- 使用 Celery、RabbitMQ 和 Redis 执行后台任务；
- 在 FastAPI 生命周期中统一创建和释放资源。

基座只提供通用机制，不包含交接班、生产事件、工单、巡检和报告的具体业务规则。

本章采用“主文总览 + 两个详细附件”的结构：

- `2.7`：身份认证与数据库权限系统，见《第02章_后端公共基础设施建设_建立JWT_OIDC与RBAC.md》；
- `2.8` 以后：除 Auth 外的其他基座，见《第02章_后端公共基础设施建设_非Auth基座详解.md》。

## 2.2 理解基座与业务模块的边界

项目采用模块化单体。所有代码仍部署为一个后端应用，但依赖方向受到约束：

```text
业务模块 ───────→ shared / ports
基础设施实现 ───→ ports
bootstrap ─────→ infrastructure / shared / modules
main.py ───────→ 最终路由与生命周期装配
```

`app/modules/` 之外的代码基本构成公共基座：

| 目录 | 职责 |
|---|---|
| `app/bootstrap` | Settings、Provider、Celery 和模型注册装配 |
| `app/ports` | 业务依赖的稳定接口和跨 Provider 数据模型 |
| `app/infrastructure` | 千问、OpenAI、本地 HTTP、文件系统和 S3 等实现 |
| `app/shared/db.py` | 异步数据库、Session 依赖和 ORM 基类 |
| `app/shared/security` | 身份、认证、授权、数据范围和安全审计上下文 |
| `app/shared/platform` | Job、配置版本、幂等、审计、工作流和 Outbox |
| `app/shared/media` | 文件名安全、摘要规范化和本地签名传输 |
| `app/main.py` | FastAPI 应用生命周期、中间件、健康检查和路由注册 |

公共基座相对独立，但不是另一个独立应用。新增业务模块时仍需在少数装配点注册模型、路由、Celery 任务、权限代码和运行时配置。

## 2.3 端口与适配器

业务模块不能直接依赖千问、OpenAI、faster-whisper、MiniCPM-V、boto3 或本地磁盘路径。否则更换模型或存储时，每个业务模块都要修改。

本项目定义四类端口：

| 端口 | 业务含义 | 当前可选实现 |
|---|---|---|
| `TextLLMProvider` | 生成经过 Pydantic 校验的结构化文本 | Fake、千问、OpenAI、OpenAI 兼容 HTTP |
| `SpeechToTextProvider` | 把音频转换成分段文本 | Fake、本地 HTTP、OpenAI、通用 HTTP |
| `VisionProvider` | 从巡检图片产生候选发现 | Fake、本地/通用 HTTP |
| `StorageProvider` | 上传授权、对象检查、读取、删除和临时物化 | Memory、本地私有文件系统、S3 兼容存储 |

端口位于 `app/ports`，实现位于 `app/infrastructure`，选择实现的代码集中在 `app/bootstrap/providers.py`。

## 2.4 统一配置、数据库和迁移

`app/bootstrap/config.py` 中的 `Settings` 以项目根目录 `.env` 为默认配置源，操作系统环境变量可以覆盖同名字段。主要配置组包括：

- 应用环境、API 前缀和 CORS；
- PostgreSQL；
- JWT/OIDC；
- 文字、ASR、视觉和存储 Provider；
- RabbitMQ、Redis 和 Celery；
- Provider 超时与重试；
- Job 心跳超时与 Outbox 重试；
- 音频、图片大小及 MIME 白名单。

生产环境会额外拒绝非 HTTPS IdP、SQLite、Fake Provider、内存存储、危险的 CORS 和不安全的存储地址。

数据库层使用：

- SQLAlchemy 2 异步引擎；
- `async_sessionmaker`；
- 统一约束命名规则；
- PostgreSQL JSONB，并为 SQLite 测试切换成 JSON；
- Alembic 管理正式模式变化。

项目运行时不应依赖 `create_all()` 修改正式数据库。开发和部署统一执行：

```bash
uv run alembic upgrade head
uv run alembic current
uv run alembic check
```

当前最新迁移为 `20260902_0003`。测试默认使用独立临时 SQLite；PostgreSQL 迁移验证应使用专门的临时数据库，不使用正在开发的 `pipechina` 数据库。

## 2.5 统一请求边界

FastAPI 请求进入应用后，会依次经过公共边界：

请求会经过 CORS、`IdempotencyMiddleware`、`request_id` 上下文、JWT认证、数据库身份映射、权限和数据范围检查，最后进入Router与Service；业务异常再由统一错误处理器转换为响应。

`X-Request-ID` 用于串联 HTTP 响应、业务日志和审计记录。带 `Idempotency-Key` 的 JSON 写请求会保存请求摘要和首次响应；同一个用户、操作和幂等键重复提交相同内容时直接回放结果，提交不同内容时返回冲突。

统一错误格式为：

```json
{
  "error": {
    "code": "CONFLICT",
    "message": "...",
    "request_id": "...",
    "details": {}
  }
}
```

业务代码抛出稳定的 `AppError` 子类，Router 不重复拼装错误 JSON。

## 2.6 本机开发运行方式

PostgreSQL、RabbitMQ、Redis 和 SeaweedFS 是多个本地项目共用的长期运行容器。项目根目录的 `docker-run` 是首次创建记录，不是每日启动脚本。

容器已经创建后使用：

```bash
docker start postgres rabbitmq redis seaweedfs
docker ps
```

宿主机中的 PyCharm、`uv`、Alembic、API 和 Worker通过映射端口访问容器，因此 `.env` 使用：

```env
DATABASE_URL=postgresql+asyncpg://peter:123456@127.0.0.1:5432/pipechina
CELERY_BROKER_URL=amqp://peter:123456@127.0.0.1:5672//
CELERY_RESULT_BACKEND=redis://127.0.0.1:6379/1
REDIS_URL=redis://127.0.0.1:6379/0
```

只有运行在 Compose 网络内部的服务才使用 `postgres:5432`、`rabbitmq:5672` 和 `redis:6379`。不要把宿主机和 Compose 两套地址混用。

常用启动命令均在项目根目录执行：

```bash
uv run alembic upgrade head
uv run uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
uv run celery -A app.bootstrap.celery_app:celery_app worker \
  -l INFO -Q audio,ai_text,vision,report,maintenance
uv run celery -A app.bootstrap.celery_app:celery_app beat -l INFO
```

`docker-compose.yml` 用于完整容器化部署或烟雾测试；“共享容器 + PyCharm 运行项目”是另一种模式，两者不要混合启动同一组 PostgreSQL 端口。

## 2.7 身份认证与数据库权限系统

认证负责回答“用户是谁”，授权负责回答“用户能做什么”，数据范围负责回答“用户能操作哪些数据”。主后端验证外部 IdP 签发的 JWT，但不保存 IdP 私钥，也不负责校验用户密码。

本节的完整概念、模型、代码、Mock IdP、初始化脚本和验证流程，见：

```text
docs/第02章_后端公共基础设施建设_建立JWT_OIDC与RBAC.md
```
