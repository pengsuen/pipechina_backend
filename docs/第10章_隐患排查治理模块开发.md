# 第10章 隐患排查治理模块开发

[文档导航](README.md) · [上一章：会议录音与知识发布](第09章_会议录音转写与知识发布.md)

本章说明`app/modules/hazard`的真实实现。模块把人工登记、巡检发现、生产事件等来源统一纳入隐患台账，并通过风险评估、整改、验收和销项形成可审计闭环。

## 10.1 模块边界

隐患模块管理的是已经进入治理流程的业务事实，不直接控制SCADA，也不把视觉模型或文字模型的建议当作最终结论。

```text
人工登记 / 巡检发现 / 生产事件 / 会议 / 交接班
                         ↓
                    隐患主记录
                         ↓
              人工风险评估与责任分派
                         ↓
                    整改和复查
                         ↓
              验收通过销项或驳回重改
                         ↓
                 关联维检工单与审计
```

当前实现包含：

- 隐患登记和来源标记；
- 5×5风险矩阵；
- 整改责任人、控制措施和完成期限；
- 整改结果提交；
- 验收通过、驳回重改和正式销项；
- 状态流转、评估、整改及验收历史；
- 乐观版本校验和数据库行锁；
- 组织数据范围及独立权限；
- 同组织维检工单关联；
- 逾期判断和列表筛选。

当前没有实现：

- AI自动确认隐患或自动定级；
- AI自动验收、自动销项；
- 隐患附件上传；
- 自动创建维检工单；
- 短信、邮件等外部催办通道；
- 设备台账和GIS定位。

这些边界避免模型建议未经人工授权直接改变正式安全生产记录。

## 10.2 代码结构

```text
app/modules/hazard/
├── api/
│   └── router.py          # HTTP 接口、查询过滤和响应组装
├── application/
│   └── service.py         # 权限、状态机、风险计算和事务
├── domain/
│   ├── models.py          # SQLAlchemy 持久化模型
│   └── schemas.py         # Pydantic 输入输出结构
└── infrastructure/
    └── __init__.py        # 预留独立仓储实现位置
```

模型统一由`app/bootstrap/model_registry.py`导入，路由在`app/main.py`注册。隐患治理表包含在`alembic/versions/20260926_0001_initial_schema.py`中。

## 10.3 数据模型

### 10.3.1 `Hazard`

`Hazard`保存隐患当前快照，主要字段如下：

| 字段 | 含义 |
|---|---|
| `hazard_no` | 系统生成的隐患编号 |
| `organization_unit_id` | 数据所属组织 |
| `title`、`description` | 隐患标题和详细描述 |
| `location`、`category` | 位置和分类 |
| `source_type`、`source_id` | 来源类型和来源记录 |
| `status` | 当前治理状态 |
| `likelihood`、`consequence` | 可能性和后果分值 |
| `risk_score`、`risk_level` | 矩阵得分和风险等级 |
| `control_measures` | 整改前临时控制措施 |
| `assignee_id`、`due_at` | 整改责任人和期限 |
| `version` | 并发控制版本号 |
| `closed_by`、`closed_at` | 销项操作人和时间 |

`source_type`支持`manual`、`inspection_finding`、`production_event`、`meeting`和`handover`。当前`source_id`是通用UUID，不设置多态外键；创建方需要保证来源真实存在，后续可按来源类型增加专用校验器。

### 10.3.2 历史表

| 模型 | 保存内容 | 是否覆盖旧记录 |
|---|---|---|
| `HazardAssessment` | 风险分值、等级、依据、评估人 | 否，按版本追加 |
| `HazardRectification` | 整改动作、结果、提交人和时间 | 否 |
| `HazardAcceptance` | 验收通过或驳回、原因和验收人 | 否 |
| `HazardTransition` | 前后状态、操作人、原因和版本 | 否 |
| `HazardWorkOrderLink` | 隐患与维检工单关系 | 重复关联复用原记录 |

主表负责快速查询当前状态，历史表负责追溯过程，不能用更新主表代替历史记录。

## 10.4 状态机

正常流程如下：

```text
pending_assessment
        ↓ assess
pending_rectification
        ↓ start-rectification
rectifying
        ↓ submit-rectification
pending_acceptance
      ↙ reject       ↘ accept
rectifying             closed
```

每次状态流转同时执行三件事：

1. 更新`Hazard.status`；
2. 将`Hazard.version`加一；
3. 追加一条`HazardTransition`。

Service会检查当前状态，非法跳转返回`409 STATE_CONFLICT`。例如待评估隐患不能直接提交整改，已销项隐患不能再次验收。

## 10.5 风险矩阵

风险分值采用：

```text
risk_score = likelihood × consequence
```

两个输入均限制为1到5。当前等级映射为：

| 分值 | 等级 | 字段值 |
|---:|---|---|
| 1–4 | 低风险 | `low` |
| 5–9 | 一般风险 | `medium` |
| 10–16 | 较高风险 | `high` |
| 17–25 | 重大风险 | `major` |

矩阵阈值集中在`risk_level_for()`，不是让调用方直接提交风险等级。这样可以防止同一分值被不同客户端解释成不同等级。实际项目如果采用另一套企业标准，应通过受控配置版本扩展，而不是由前端自由传值。

## 10.6 并发与事务

状态修改接口必须提交`expected_version`。Service先对隐患行执行`SELECT ... FOR UPDATE`，再比较请求版本和数据库版本：

```text
请求 expected_version = 数据库 version → 允许继续
请求 expected_version ≠ 数据库 version → 返回 409
```

行锁解决同时修改问题，版本号解决用户拿着旧页面提交的问题。评估、状态流转、历史记录和安全审计在同一事务内提交，任一步失败都不会留下半套业务数据。

## 10.7 权限设计

隐患模块定义六项权限：

| 权限 | 作用 |
|---|---|
| `hazard:read` | 查看隐患台账和治理轨迹 |
| `hazard:create` | 登记隐患 |
| `hazard:assess` | 风险评估及责任分派 |
| `hazard:rectify` | 开始整改和提交整改结果 |
| `hazard:accept` | 验收、驳回和销项 |
| `hazard:link` | 关联维检工单 |

内置角色`hazard_manager`拥有完整隐患治理权限和工单读取权限。`inspection_operator`可以查看和登记隐患，但不能自己完成风险定级或销项。

权限检查分为两层：

- 路由依赖检查是否拥有操作权限；
- Service检查目标记录是否处于用户的数据范围内。

整改操作额外支持`ASSIGNED`范围，使整改责任人可以处理分派给自己的记录。

## 10.8 API

| 方法 | 路径 | 作用 |
|---|---|---|
| `POST` | `/api/v1/hazards` | 登记隐患 |
| `GET` | `/api/v1/hazards` | 查询隐患列表 |
| `GET` | `/api/v1/hazards/{hazard_id}` | 查看主记录和完整轨迹 |
| `POST` | `/api/v1/hazards/{hazard_id}:assess` | 风险评估和责任分派 |
| `POST` | `/api/v1/hazards/{hazard_id}:start-rectification` | 开始整改 |
| `POST` | `/api/v1/hazards/{hazard_id}:submit-rectification` | 提交整改结果 |
| `POST` | `/api/v1/hazards/{hazard_id}:accept` | 验收通过并销项 |
| `POST` | `/api/v1/hazards/{hazard_id}:reject` | 驳回并退回整改 |
| `POST` | `/api/v1/hazards/{hazard_id}/work-orders` | 关联维检工单 |

列表接口支持`status`、`risk_level`和`overdue`过滤，以及`limit`、`offset`分页。`overdue`不是持久化状态，而是根据`due_at`、当前时间和是否已结束动态计算。

## 10.9 示例流程

先登记隐患：

```json
{
  "title": "阀门填料函渗漏",
  "description": "巡检发现阀门填料函存在轻微渗漏",
  "location": "北京输气站二号阀室",
  "category": "设备设施",
  "source_type": "inspection_finding",
  "source_id": "来源记录 UUID"
}
```

再由有权限的人员评估：

```json
{
  "likelihood": 4,
  "consequence": 5,
  "rationale": "泄漏可能扩大并造成重大后果",
  "control_measures": "设置警戒并加强泄漏检测",
  "assignee_id": "整改责任人 UUID",
  "due_at": "2026-09-22T18:00:00+08:00",
  "expected_version": 1
}
```

系统计算得到`risk_score=20`、`risk_level=major`，并进入`pending_rectification`。后续每次请求都必须使用最新响应中的`version`。

## 10.10 测试与验收

模块测试位于`tests/test_hazard_flow.py`，覆盖：

- 登记隐患；
- 重大风险计算；
- 过期版本冲突；
- 开始和提交整改；
- 验收驳回后再次整改；
- 二次提交后验收销项；
- 完整评估、整改、验收和状态历史；
- 禁止设置过去的整改期限。

运行模块测试：

```bash
.venv/bin/pytest -q tests/test_hazard_flow.py --tb=short
```

验证迁移一致性：

```bash
uv run alembic upgrade head
uv run alembic check
```

投产前还需要结合企业风险分级制度确认矩阵阈值，并补充真实角色授权、跨组织隔离、并发压测、通知升级和备份恢复验收。
