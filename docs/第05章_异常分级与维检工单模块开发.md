# 第5章 异常分级与维检工单模块开发

[文档导航](README.md) · [上一章](第04章_生产运行事件抽取与归档模块开发.md) · [下一章](第06章_巡检图片分析与隐患上报模块开发.md)

本章横跨两个模块：事件模块拥有多Agent调查和只读MCP工具服务，维检模块拥有评估审核与工单。公共层提供任务、租约、日志等机制；项目没有额外的通用Agent微服务。

## 5.0 智能体的基本概念

### 5.0.1 从一次模型调用到智能体

假设有一条已经确认的事件：“某站场设备出现压力波动，原因待查。”

一次普通模型调用可以要求模型把这段话整理为分类、风险等级和建议。但模型仅凭这句话，不知道数据库里是否有类似事件，也不知道相关工单是否已经处理完成。即使输出格式正确，也不代表判断有足够依据。

智能体是在目标和约束下，让模型根据当前信息决定下一步行动的程序。例如：先查询同类事件，读到结果后判断还需要哪些证据，再查询相关工单，最后决定是否结束取证。

```text
普通模型调用：输入 -> 模型生成结果 -> 程序校验

智能体循环：目标与已有信息 -> 模型决定下一步
                              ├─ 请求工具 -> 程序执行 -> 返回结果 -> 再决策
                              └─ 结束 -> 返回结果
```

一个最小智能体通常需要目标、模型、工具、状态、控制循环和停止条件。它不一定需要多个模型或独立服务，也不是给提示词加上“你是一名专家”就自动成为智能体。关键在于模型是否参与决定接下来做什么，以及程序是否执行和反馈这些决定。

### 5.0.2 模型、工具、工作流、智能体分别负责什么

| 概念 | 负责什么 | 本章中的例子 |
|---|---|---|
| 大语言模型（LLM） | 理解输入、提出下一步动作、生成分析或建议 | 判断下一步查历史事件还是工单 |
| 工具（Tool） | 读取外部事实或执行确定性操作 | 按权限查询已确认事件 |
| 工作流（Workflow） | 按代码规定的路径和条件组织步骤 | 取证后评估风险，再生成方案、复核和审核 |
| 智能体（Agent） | 在受控范围内动态决定步骤或工具 | 根据新证据决定继续查询或结束 |
| 状态机 | 规定业务对象允许怎样改变状态 | 工单从草稿到审批、派发、解决和关闭 |

工作流和智能体可以组合使用。固定、可预期的步骤由代码组织；需要根据新信息调整动作的局部环节交给智能体。本章采用的就是“外层固定流程，内部动态取证”。

模型负责提出建议，工具负责获得事实，业务服务负责授权、校验与事务。模型说“应当创建工单”，并不等于工单已经创建，也不代表当前用户有权创建。

### 5.0.3 工具调用：模型提出请求，程序真正执行

通用工具通常包含名称、用途描述、参数模式和执行函数。名称与描述帮助模型选择工具，参数模式说明输入要求，执行函数才真正访问数据库或外部接口。

本章的模型可能返回如下决策：

```json
{
  "action": "search_work_orders",
  "query": "压力波动",
  "unknowns": []
}
```

这只是一个查询请求。接下来由程序依次完成：校验结构、检查工具白名单、按用户权限和事件所属组织执行查询、保存证据，再把结果放入下一次模型请求。模型不能直接拿到数据库连接，也不能提交任意SQL。

本项目只注册`search_events`、`search_work_orders`、`search_handover`三个调查工具；`finish`是停止动作，不是查询工具。参数约束集中在`EvidenceDecision`中，工具注册表公开名称、来源标签和只读标记，尚未提供通用工具那样丰富的用途描述和逐工具参数模式。

### 5.0.4 ReAct：决策、行动、观察，再决策

ReAct表示推理与行动交替进行。理解时可以关注三个可观察环节：模型决定下一步、程序执行动作、模型收到执行结果。

下面是用于理解的示意过程，不是项目中已经发生的调查记录：

```text
已知：事件描述提到压力波动，原因未确认
  -> 决策：查询类似历史事件
  -> 行动：执行 search_events
  -> 观察：找到一条已确认事件及其描述
  -> 决策：证据还不足，查询相关工单
  -> 行动：执行 search_work_orders
  -> 观察：获得工单状态和描述
  -> 决策：结束取证，把尚未确定的原因列入 unknowns
```

循环的意义在于，后一步可以依赖前一步的新信息；查询到相似记录并不能直接证明本次事件具有相同原因。

循环必须有边界。本章最多进行六次取证决策，`finish`也占一次，因此成功路径最多查询五次；连续六次都查询会失败。程序还限制总时长、拒绝重复的工具与查询组合。

需要记录的是工具名、查询词、证据和输出等外部行为，不是模型隐藏的内部思维过程。

### 5.0.5 多智能体：按职责协作，不等于多个模型或并行运行

多智能体把复杂任务拆分为不同角色，让每个角色围绕较明确的目标处理输入并交付结果。例如取证角色寻找事实，风险角色做分类分级，复核角色检查前面的产物。

多个角色可以使用同一个模型Provider，运行在同一个进程，并按顺序执行。角色数量、模型数量、进程数量和并发数量是四件不同的事。

| 本章角色 | 输入与职责 | 交付物 |
|---|---|---|
| Coordinator（协调） | 查看事件，返回规定角色列表和调查重点 | `CoordinatorPlan` |
| Evidence（取证） | 根据事件与已有证据动态选择只读查询或结束 | `EvidenceReport` |
| Risk（风险） | 根据事件和证据形成分类、风险及依据 | `RiskReport` |
| Plan（方案） | 根据风险与证据形成处置建议 | `PlanReport` |
| Critic（复核） | 检查风险和方案输出，以及合法证据ID列表 | `CriticReport` |

正常路径依次执行Coordinator、Evidence、Risk、Plan、Critic。Evidence可在单个节点内多次选择工具；Critic要求补证据或修订方案时，图会返回相应节点。Coordinator的`focus`会进入后续输入，但不改变图的节点关系。

这种拆分便于约束输入、保存产物和定位问题，但也增加模型调用和延迟。多个角色可能重复同一种错误；Critic是额外的复核角色，不是独立事实正确性的保证，更不能替代人工授权。

### 5.0.6 结构化输出、任务规划与处置方案的区别

结构化输出是让模型返回符合约定的数据对象。例如`RiskReport`要求输出分类、风险等级、依据和证据引用。项目通过Provider请求JSON Schema结果，再通过Pydantic校验。

结构正确只说明字段和类型符合约定。证据是否真实、引用是否支持结论、用户是否有权执行操作，仍然需要其他校验。

工具调用可以用结构化对象表达，但不是所有结构化输出都会触发工具。`EvidenceDecision`用于选择下一步动作；`RiskReport`和`PlanReport`主要是业务分析产物。

### 5.0.7 状态、上下文、记忆与运行记录

| 概念 | 应怎样理解 | 当前项目情况 |
|---|---|---|
| 状态 | 程序执行到哪里、已经获得什么 | 运行状态、角色输出、累积证据、剩余决策步数 |
| 上下文 | 本次实际发送给模型的信息 | 按角色组装事件描述、证据和上游结果，并非所有历史记录都发送 |
| 运行记录 | 保存执行过程，供查询和审计 | `AgentRun`、`AgentTask`、`AgentStep`、`AgentEvidence`等 |
| 长期记忆 | 跨任务保存并主动召回历史经验或用户偏好 | 当前调查链没有此机制 |
| 断点恢复 | 从保存的执行位置继续，而不是全部重跑 | 事件调查使用PostgreSQL checkpoint；任务重试仍按业务规则处理运行身份和授权 |

数据库里保存了历史事件，只有工具实际查出并传给模型后，它们才成为本次模型上下文。历史数据、知识库和长期记忆不能直接画等号。

`agent_models.py`定义的是数据库实体。`ContextVar`用于传递当前异步调用的用量信息，不是模型记忆。

### 5.0.8 人在回路：建议与业务执行之间的边界

人在回路（Human-in-the-loop）是把人的判断放入关键决策节点，而不只是事后查看模型结果。本章让智能体读取证据和提出建议，后续由具有权限的人员批准或驳回。

```text
模型建议 → 程序校验 → 保存待审核评估与工作流
                         ├─ 人工驳回 -> 结束
                         └─ 人工批准 -> 业务代码创建工单草稿
```

审核时还要检查源事件版本是否改变，避免批准已经过时的调查结果。工单的审批、派发和关闭继续受权限和状态机控制。

工具边界要由程序保障：白名单限定可调用动作，权限过滤限定可见数据，参数校验约束输入，幂等与并发控制防止重复产生业务结果。提示词中的“不要越权”不能替代这些机制。

### 5.0.9 如何判断智能体是否可靠

既要检查结果，也要检查过程：有没有查对资料，是否重复查询，引用能否支持结论，是否把未知原因说成确定事实，以及人工审核和权限限制是否生效。

项目已经记录步骤、证据、耗时和模型用量，并设置轮数与总时长限制。

### 5.0.10 常见智能体框架及适用问题

智能体框架把模型调用、工具执行、消息传递、状态管理或角色协作等重复代码组织成可复用组件。使用框架可以减少基础工作，但业务授权、数据库事务、证据有效性和人工审核规则仍要由应用实现。

相关框架的职责如下。

| 框架 | 主要定位与核心概念 | 在本章场景下如何理解 |
|---|---|---|
| [LangChain](https://docs.langchain.com/oss/python/langchain/overview) | 提供模型、工具和可配置智能体组件，`create_agent`用于组装工具调用智能体；其智能体建立在LangGraph之上 | 适合理解标准模型—工具循环，减少手写消息和工具调度代码 |
| [LangGraph](https://docs.langchain.com/oss/python/langgraph/overview) | 用状态、节点、边和条件路由组织流程，可支持持久执行和人工介入 | 事件调查已配置PostgreSQL checkpoint；报告分组图没有配置checkpoint |
| [CrewAI](https://docs.crewai.com/en/introduction) | 用Agent、Task、Crew组织角色协作，用Flow管理更明确的执行流程和状态 | 可把取证、风险、方案等职责映射成角色任务，但权限和工单规则仍属于业务服务 |
| [LlamaIndex](https://developers.llamaindex.ai/python/framework/) | 围绕数据接入、索引检索、RAG，以及使用数据工具的智能体和工作流构建应用 | 更容易与第8章企业知识检索结合理解；它不只是一个向量数据库，也不局限于普通问答 |


框架的能力有重叠，不能简单按“单智能体用某框架、多智能体只能用另一个框架”划分。LangGraph可以组织多个角色，CrewAI也有确定性Flow；最终要看流程控制、状态恢复、模型兼容和业务集成要求。


### 5.0.11 综合对比
项目中的模型、编排和工具边界如下：

| 层次 | 回答的问题 | 本项目的实现 |
|---|---|---|
| 模型Provider | 模型请求发给谁，返回结果如何解析？ | `TextLLMProvider`与OpenAI兼容、Qwen、Fake等适配器 |
| 智能体编排 | 下一步由谁决定，工具结果怎样进入下一轮？ | `investigation.py`中的固定角色链与取证循环 |
| 工具实现 | 怎样读取所需业务事实？ | `investigation_tools.py`中的注册表与权限查询 |
| 图与工作流 | 步骤、状态和分支怎样组织？ | 部分业务使用LangGraph；本章审核图处理人工决定后的路由 |
| 工具连接协议 | 不同应用怎样以统一方式暴露和调用工具？ | 内部调查使用进程内函数；外部客户端可通过`/mcp/`调用三个只读工具 |
| 业务可靠性 | 谁有权限，怎样提交结果和避免重复执行？ | 授权、数据库事务、任务Outbox、租约与业务状态机 |

MCP是工具与上下文连接协议。项目在`/mcp/`提供只读调查工具；智能体决策循环由调查流程实现。

项目使用自定义Provider、调查工具注册表和LangGraph调查图；Evidence角色执行受限工具循环，调查图使用PostgreSQL checkpoint。报告分组另有独立的LangGraph流程。当前调查不使用CrewAI、AutoGen或LlamaIndex，也没有跨任务主动召回的长期记忆机制。

### 5.0.12 调查图的持久化与重试

调查图在`investigation.py`中定义Coordinator、Evidence、Risk、Plan和Critic五个节点。正常路径依次执行五个节点；Critic判为`insufficient_evidence`时返回Evidence，判为`needs_revision`时返回Plan，最多进行两轮修订。Evidence的工具决策另有六次上限，整次图执行限时600秒。

图使用`AsyncPostgresSaver`，检查点保存在PostgreSQL的`agent_checkpoints`schema，`thread_id`为当前`AgentRun.id`。每个节点同步持久化检查点；同一运行再次进入图时，先读取已有图状态，再继续执行。检查点保存的是图执行状态，业务结果仍由`AgentRun`、`AgentTask`、`AgentStep`、`AgentEvidence`、`AgentProposal`和审核工作流管理。

公共Job重试会创建新的`AgentRun`，使用新的图线程，不沿用上一尝试的检查点。执行前后仍需校验租约、事件版本、取消请求及当前用户权限。检查点不代替这些业务约束，也不表示失败事务中的全部步骤日志都已提交。

对外查询入口为`GET /api/v1/agent-runs/{run_id}`及其步骤、证据、质量接口。带专家标签的离线评测见本章5.13节，外部MCP工具接入见本章5.12节，内部调查的工具调用不经过该HTTP端点。


## 5.1 本章目标

```text
接收第4章已确认生产事件
  -> 创建异常分类分级任务
  -> Coordinator返回角色清单和调查重点
  -> Evidence Agent通过ReAct与进程内只读工具收集历史事件、工单和交接证据
  -> Risk、Plan和Critic完成分级、方案与角色复核
  -> 生成带证据的分类、风险等级和处置建议
  -> 保存 AbnormalityAssessment
  -> 创建 WorkflowRun 等待人工审核
  -> 审核驳回：流程结束
  -> 审核通过：确定性代码创建草稿工单
  -> 工单提交复核、审批、派发、执行、解决和关闭
  -> 保存状态时间线、附件和超期提醒
```

本章的核心安全原则是：智能体可以查询只读证据并提出分类分级建议，但不能批准自己的建议，也不能直接创建、派发、解决或关闭工单。高风险业务动作始终由权限校验、人工决定和确定性状态机控制。

**本节文件：** 先读`app/modules/maintenance_order/`，再读`app/modules/operation_event/application/service.py`中的分类入口、`app/shared/platform/models.py`中的`WorkflowRun`，理解异常评估、人工审核和工单状态机之间的关系。

### 5.1.1 本章先理解的概念

| 概念 | 含义 | 本章中的作用 |
|---|---|---|
| 智能体 | 能围绕目标保存状态、选择工具并多步执行的受控程序 | 对已确认事件开展证据调查和方案生成 |
| 多智能体 | 按职责拆分的多个Agent角色协作 | 分离计划、取证、风险、方案和复核职责 |
| ReAct | 动作、工具执行、观察、再决策的循环 | Evidence Agent根据已有证据决定下一次工具查询或结束 |
| 工具注册表 | 模型与业务查询之间的进程内受控边界 | 只开放经过注册、授权和限量的业务查询；另有MCP协议适配层 |
| Workflow | 按预设规则流转并保存业务状态的流程 | 数据库保存待审核状态，审核接口处理人工决定；不等于图的断点恢复 |
| 状态机 | 明确允许和禁止的状态转换 | 控制工单从草稿到关闭的完整生命周期 |

#### 表关系与实际写入边界

- `AgentRun`通过外键固定事件和事件版本，删除策略为`RESTRICT`；`job_id`唯一且删除Job时置空。按事件/状态、组织/创建时间建立索引。
- `AgentTask`的`(run_id, role)`唯一；`AgentStep`的`(task_id, step_index)`唯一；建议表和质量表的`run_id`分别唯一。重试必须创建新运行，不能沿用旧运行的角色键。
- 任务、证据、建议和质量记录对运行的外键使用`CASCADE`，步骤对任务也使用`CASCADE`。这些数据库约束不代表业务接口提供删除功能。
- `AgentTask.input_snapshot`保存修订轮次等节点输入，`depends_on`记录角色依赖；`AgentStep.parent_span_id`当前调用路径没有赋值。
- `AgentProposal.review_status`初始为`pending`；后续业务评估另存为`AbnormalityAssessment`，不能将两者理解为同一条审核记录。
- `AgentRun.current_stage`初始为`coordinator`，执行中随角色更新，成功后改为`human_review`。模型和工具步骤分别计数；异常回滚可能清除未提交的步骤和用量记录。

## 5.6 理解多智能体、ReAct与MCP

### 5.6.1 什么是智能体

基础概念、常见框架与本项目的对应关系已在5.0节介绍。本节转向代码中的具体结构和执行边界。

普通模型调用的步骤由业务代码提前固定：输入一段文本，要求模型按指定Schema返回结果，然后流程结束。智能体则是在一个受控循环中，让模型根据目标、已有信息和中间观察结果决定下一步行动。

一个最小智能体通常包含：

| 组成部分 | 作用 |
|---|---|
| 目标 | 告诉模型最终要完成什么，例如形成异常分类分级建议 |
| 状态 | 保存当前输入、历史工具结果、剩余步数和已取得证据 |
| 工具 | 允许模型读取或操作外部系统的受控接口 |
| 决策模型 | 在每一步选择工具、生成参数或结束任务 |
| 控制循环 | 执行模型决定、返回观察结果并决定是否继续 |
| 终止条件 | 限制最大步数、总超时、重复调用和最终输出结构 |
| 审核边界 | 决定智能体结果能否直接生效；本章结果必须人工审核 |

“调用了大模型”不等于“使用了智能体”。第四章事件抽取只有一次`generate_structured()`，没有动态工具选择和多步循环，因此不是智能体。本章分类阶段允许模型根据观察结果继续选择工具或结束，才属于智能体。

### 5.6.2 多智能体协作与ReAct

本项目使用职责隔离的五智能体协作；Evidence Agent内部使用ReAct工具循环：

```text
Coordinator 返回角色清单和调查重点（执行顺序固定）
  -> Evidence 通过受控工具 收集证据
  -> Risk 分类分级
  -> Plan 形成处置建议
  -> Critic 复核证据和结论
  -> 创建 AgentProposal
  -> 人工审核
```

本项目不会保存或展示模型的内部思维过程。持久化的是可审计的工具名称、查询词、工具结果、最终证据ID和未知项，这些是外部行为轨迹，不是隐藏推理文本。

### 5.6.3 进程内工具边界与MCP的区别

工具注册表位于Agent与业务数据之间。模型只能选择服务端注册的工具名并提交普通查询词，不能获得数据库连接、SQL、用户令牌或任意网络访问能力。`event-tools`、`work-order-tools`和`handover-tools`是三个进程内来源标签，不是三个MCP服务器；内部调查的调用结果保存为带来源、版本、内容哈希和访问范围的`AgentEvidence`。外部客户端可通过单独的`/mcp/` Streamable HTTP服务访问同三项只读查询，服务端逐次校验JWT、当前用户权限及事件数据范围，完整接口见本章5.12节。

### 5.6.4 本项目智能体的安全边界

- 工具仅支持查询，不能创建、修改或删除业务记录。
- 模型只能提交最长100字符的普通查询词，不能提交SQL、组织ID或任意工具名。
- 每次查询强制限定为目标事件所属组织，并再次应用当前用户数据范围。
- 每个工具最多返回最近5条记录，单条正文最多返回2000字符。
- Evidence Agent最多进行6次决策，`finish`也占一次；必须在预算内返回`finish`，因此成功路径最多查询工具5次。六次都选择查询会在循环结束后失败；模型调用和工具调用分别记为步骤，`step_count`不等于决策次数。整个协作运行不超过600秒。
- 相同工具和查询词不能重复调用。
- 最终采用的Critic `evidence_ids`必须属于初始事件版本或工具已保存的证据集合。当前不强制引用列表非空，也不逐一验证Risk、Plan输出中的引用，引用合法不等于结论正确。
- Agent只能产生待审核候选，不能自己批准评估或创建工单。

### 5.6.5 `domain/agent_schemas.py`：全部结构化输出字段

`CoordinatorPlan`、`EvidenceDecision`、`EvidenceReport`、`PlanReport`和`CriticReport`继承`StrictProviderOutput`，拒绝未定义字段；`RiskReport`继承`AssessmentCandidate`。下面列出本文件直接声明的字段；没有默认值的字段为必填。

#### `CoordinatorPlan`

约束协调角色返回的专业角色列表和调查重点。

| 字段 | 类型 | 当前定义与作用 |
|---|---|---|
| `roles` | `list[Literal['evidence', 'risk', 'plan', 'critic']]` | 需要包含的专业角色列表；`min_length=4`、`max_length=4` |
| `focus` | `list[str]` | 协调角色提出的调查重点；`default_factory=list`、`max_length=10` |

#### `EvidenceDecision`

约束取证角色下一步查询或结束取证的决策。

| 字段 | 类型 | 当前定义与作用 |
|---|---|---|
| `action` | `Literal['search_events', 'search_work_orders', 'search_handover', 'finish']` | 步骤动作或取证决策 |
| `query` | `str` | 最长一百字符的普通查询词；`max_length=100` |
| `unknowns` | `list[str]` | 尚未确定的事项；`default_factory=list`、`max_length=20` |

#### `EvidenceReport`

汇总已保存的证据标识、事实文字和未知事项。

| 字段 | 类型 | 当前定义与作用 |
|---|---|---|
| `evidence_ids` | `list[str]` | 引用的已保存证据标识 |
| `facts` | `list[str]` | 证据中的事实文字 |
| `unknowns` | `list[str]` | 尚未确定的事项 |

#### `RiskReport`

约束风险角色输出的分类分级结论与证据引用。

| 字段 | 类型 | 当前定义与作用 |
|---|---|---|
| `evidence_ids` | `list[str]` | 引用的已保存证据标识 |
| `unknowns` | `list[str]` | 尚未确定的事项；`default_factory=list` |

#### `PlanReport`

约束方案角色输出的处置建议、优先级和参与职责。

| 字段 | 类型 | 当前定义与作用 |
|---|---|---|
| `recommended_action` | `str` | 建议的处置措施 |
| `priority` | `Literal['low', 'medium', 'high', 'critical']` | 建议的处置优先级 |
| `required_roles` | `list[str]` | 建议参与处置的职责；`default_factory=list` |
| `evidence_ids` | `list[str]` | 引用的已保存证据标识 |
| `high_risk_actions` | `list[str]` | 方案识别的高风险动作；`default_factory=list` |

#### `CriticReport`

约束复核角色的审核结论、问题、冲突和证据引用。

| 字段 | 类型 | 当前定义与作用 |
|---|---|---|
| `decision` | `Literal['approved_for_human_review', 'needs_revision', 'insufficient_evidence']` | 复核结论 |
| `issues` | `list[str]` | 需要修正的问题；`default_factory=list` |
| `conflicts` | `list[str]` | 复核发现的冲突；`default_factory=list` |
| `evidence_ids` | `list[str]` | 引用的已保存证据标识 |


`RiskReport`还继承`AssessmentCandidate`的`category`、`risk_level`、`rationale`、`recommended_action`，字段定义见5.4.7和`app/ports/models.py`。最终建议的处置动作取自`PlanReport.recommended_action`。

契约校验与编排校验分开：`CoordinatorPlan.roles`长度固定为四，编排另检查四种角色齐全；实际顺序不由返回列表决定。`EvidenceDecision.query`即使`finish`也必须提供，可以为空字符串。`RiskReport`、`PlanReport`的引用没有逐项做来源集合校验，最终采用的是通过集合校验的Critic引用。`priority`、`required_roles`、`high_risk_actions`保存在方案角色输出中，没有据此自动派发工单。

### 5.6.6 `InvestigationToolRegistry`：受控只读工具

- **功能：** 注册只读 进程内工具、拒绝未知或写工具，并把工具结果持久化为证据。
- **重要参数：** Agent Run、Agent Task、工具名和最长100字符的查询词。
- **返回：** `list[AgentEvidence]`。
- **关键规则：** 每次查询强制执行组织和权限范围，最多返回5条结果；模型不能提交SQL。

### 5.6.7 `run_multi_agent_assessment()`：协作运行时

- **功能：** 创建并执行五个持久化AgentTask，保存AgentStep和AgentEvidence，Critic通过后创建AgentProposal。
- **重要参数：** AgentRun、事件及固定版本、文字模型Provider和InvestigationToolRegistry。
- **返回：** `AgentProposal`。
- **关键规则：** 角色切换及取证决策前检查取消；重复工具调用、非法风险等级和Critic引用未知证据会失败。Critic要求修订时，图按决定返回Evidence或Plan节点，最多修订两轮；仍未通过则失败。Coordinator的`roles`只检查角色齐全，实际顺序由图固定。`current_stage`随执行节点更新，成功后改为`human_review`。

### 5.6.8 答案质量、Token、成本与链路监控

运行时为模型调用和工具动作建立日志、`trace_id`、`span_id`及耗时记录。供应商未提供的Token/请求ID可以为空；汇总中零用量不代表免费。价格目前由分类入口写为0，没有价格管理入口，所以成本不能作为实际账单。日志与业务事务提交，异常回滚不保证留下所有中间步骤。

成功形成方案后保存`AgentQualityEvaluation`：有引用、引用ID合法、关键字段非空等基础规则与Critic结果汇总为分数。`critic_score`和`model_judge_score`来源于同一次Critic批准结果，不是额外独立评测调用。分数不是事实准确率，不能绕过人工审核；细则见第3章2.19.10。

## 5.7 创建并执行分类分级任务

这两个Service方法位于`operation_event/application/service.py`，但属于本章从已确认事件进入评估审核的入口。

### 5.7.1 `classify_event()`

- **功能：** 为已确认事件的当前版本创建`event_classification` Job，把事件版本ID写入配置快照，并投递到`maintenance`队列；内联模式直接调用执行方法。
- **重要参数：** `event`、`user`、文字模型`provider`和`inline`；用户需要`EVENT_CLASSIFY`权限。
- **返回：** `tuple[UUID, WorkflowRun | None, AbnormalityAssessment | None]`。异步模式只返回Job ID，内联模式还返回工作流和评估记录。
- **关键规则：** 锁定事件后检查`confirmed`与当前版本；复用活动分类任务，避免先创建孤立AgentRun。新任务快照包含`event_version_id`、`agent_run_id`与业务重试标识。

### 5.7.2 `execute_event_classification()`

- **功能：** 外层`execute_event_classification()`管理公共租约与失败收尾；内部`_execute_event_classification()`创建工具注册表、运行调查，再保存待审核评估和`WorkflowRun`。
- **重要参数：** `job`、`event`、快照指定的`version`、`user`和文字模型`provider`。
- **返回：** 成功返回工作流与评估元组。租约已占用、任务不可领取等情况拒绝执行；不能把拒绝领取解释成成功重放。
- **关键规则：** 领取独占执行令牌并后台续租；调查前恢复当前用户；提交结果前`guard_execution()`检查执行权，再复核当前权限和事件版本。工具注册表使用调查开始时的用户上下文，并非每次工具调用都重新加载授权。评估初始为`pending`，工作流初始为`awaiting_review/human_review`。

### 5.7.3 `_classify()`：分类Worker异步入口

- **功能：** 根据Job ID加载事件和任务快照指定的事件版本，恢复任务用户并调用`execute_event_classification()`。
- **重要参数：** 字符串形式的`job_id`。
- **返回：** Job最终状态字符串。
- **异常处理：** 已领取执行权后的失败由分类执行器按token单独落库，Task不再用旧Job对象覆盖其他执行者的状态。领取前失败或租约冲突直接抛出，不把正在运行的其他尝试改成失败。

### 5.7.4 `classify_event_task()`：Celery分类任务

- **功能：** 注册名为`app.modules.operation_event.classify_event`的Celery任务，通过`asyncio.run()`调用异步`_classify()`。
- **重要参数：** `job_id`。
- **返回：** 包含`job_id`和`status`的字典。
- **关键配置：** `acks_late=True`，执行完成后才确认消息。

### 5.7.5 重试与运行关联

公共`POST /api/v1/jobs/{job_id}:retry`通过装配钩子调用`bind_classification_retry()`。仅允许失败或取消的最新尝试重试；原事件必须仍为同一已确认版本。新Job使用新AgentRun，旧尝试中已提交的角色任务、步骤和证据保留，不复用`run_id + role`唯一键；失败事务内尚未提交的中间记录可能回滚，不能保证每次失败都留下完整轨迹。

同一业务运行的多个角色共用一个Celery任务和选定的文字Provider。正常路径按图的节点顺序执行；Critic可触发有限次数的回退。Evidence角色最多进行六次受控取证决策，图不会动态生成新角色或无限循环。

### 5.7.6 `retry.py`：`bind_classification_retry()`

- **输入：** 数据库`session`、原任务`original`、公共层已创建的新任务`retried`、操作用户`user`。
- **校验：** 加行锁读取原任务关联事件，要求仍为已确认状态并校验`EVENT_CLASSIFY`数据范围；按原任务快照读取旧AgentRun，要求事件当前版本仍等于旧运行固定版本。
- **写入：** 创建`queued/coordinator`的新AgentRun，使用新的`trace_id`，复制原运行配置并关联新Job；`flush`后只替换新任务快照中的`agent_run_id`。
- **返回与事务：** 隐式返回`None`；不自行提交，由公共重试事务统一提交新Job、Outbox和运行关联。事件版本变化时应重新分类，不能重试旧快照。

### 5.7.7 `_execute_event_classification()`：租约内的业务执行

该内部方法除事件、固定版本、任务、用户和Provider外，还接收外层取得的`execution_token`。先检查任务状态和取消标记，再校验当前事件已确认且版本属于该事件；提交前置状态后，验证快照AgentRun与事件版本一致，恢复用户授权并运行调查。

成功取得建议后重新读取Job并检查取消；用`guard_execution()`核验执行令牌，再锁定事件、重新加载用户授权，复核事件仍为同一已确认版本。只有通过这些检查，才创建`pending`的`AbnormalityAssessment`和`awaiting_review/human_review`的`WorkflowRun`，标记Job成功并一起提交。工作流快照保存事件版本、运行、建议、证据、未知项和冲突，供后续人工审核。

终态或可见取消路径返回`(None, None)`；正常返回`(workflow, assessment)`。执行异常交由外层租约包装器回滚，并在仍持有相同执行令牌时独立记录失败。不能将该内部方法脱离外层租约直接作为Worker入口。

### 5.7.8 `router.py`：`post_classify()`

接口为`POST /api/v1/events/{event_id}:classify`，状态码202，入口要求`EVENT_CLASSIFY`权限。Router从应用状态取得文字Provider和内联配置，调用`classify_event()`，再按返回的Job ID查询AgentRun。

响应包含`job_id`、`agent_run_id`、`workflow_id`、`assessment_id`。异步模式或复用活动任务时，后两项为`null`；内联执行成功才立即获得工作流和评估。HTTP 202表示接口已接受处理，不能单凭状态码判断调查或人工审核已完成。

## 5.8 Workflow确定性审核路由

Agent的动态决策和人工审核后的确定性路由是两种不同机制。`workflow.py`中的LangGraph不调用模型，只根据已经提交的`approved`布尔值选择批准或驳回分支；数据库中的`WorkflowRun`才是可查询、可审计的持久化状态。

### 5.8.1 `MaintenanceState`

| 属性 | 类型 | 作用 |
|---|---|---|
| `approved` | boolean | 人工是否批准评估 |
| `review_reason` | string | 人工审核理由 |
| `decision` | string | 图执行后得到的`approved`或`rejected` |

### 5.8.2 `route_review()`

- **功能：** 根据`state.approved`选择`approved`或`rejected`节点。
- **参数：** `MaintenanceState`。
- **返回：** 节点名称字符串。

### 5.8.3 `mark_approved()`与`mark_rejected()`

- **功能：** 构造对应分支的结果状态，保留审核理由并写入决定。
- **参数：** 当前`MaintenanceState`。
- **返回：** 更新后的`MaintenanceState`。

### 5.8.4 `build_maintenance_graph()`

- **功能：** 创建并编译`START -> 条件路由 -> approved/rejected -> END`图。
- **返回：** 编译后的LangGraph；使用`lru_cache`在进程内复用同一图实例。

### 5.8.5 `resolve_maintenance_review()`

- **功能：** 把人工决定和理由提交给确定性图，并返回最终决定。
- **重要参数：** `approved`、`reason`。
- **返回：** `approved`或`rejected`字符串。

## 5.9 Service层方法详解

### 5.9.1 `get_workflow()`

- **功能：** 查询工作流；不存在时抛出`NotFoundError`。
- **重要参数：** `session`、`workflow_id`。
- **返回：** `WorkflowRun`。

### 5.9.2 `review_workflow()`

- **功能：** 锁定等待审核的工作流，验证生产事件仍为评估时的已确认版本，加载评估记录并执行确定性审核路由。驳回时结束流程；批准时创建草稿工单和第一条状态时间线。
- **重要参数：** `workflow`、人工决定`approved`、审核`reason`和具有`MAINTENANCE_REVIEW`权限的`user`。
- **返回：** 批准时返回`WorkOrder`，驳回时返回`None`；若该工作流已有工单则返回已有工单。
- **关键规则：** 工作流使用行锁；事件在评估后发生变化时必须重新评估；工单描述由事件当前描述和评估建议组成；唯一约束保证每个工作流最多一张工单。

### 5.9.3 `get_work_order()`

- **功能：** 查询工单；不存在时抛出`NotFoundError`。
- **重要参数：** `session`、`order_id`。
- **返回：** `WorkOrder`。

### 5.9.4 `transition_work_order()`

- **功能：** 统一执行工单状态转换、乐观锁校验、负责人和期限更新、时间线写入及审计记录。
- **重要参数：** `order`、目标状态`target`、转换`reason`、`expected_version`、`user`、本次操作要求的`permission`，以及派发时可选的`assignee_id`和`due_at`。
- **返回：** 转换后的`WorkOrder`。
- **关键规则：** 预期版本必须等于当前版本；目标状态必须存在于`ALLOWED_TRANSITIONS[当前状态]`；成功后版本号加1并提交事务。

状态转换表：

| 当前状态 | 允许进入的状态 |
|---|---|
| `draft` | `pending_review`、`cancelled` |
| `pending_review` | `approved`、`draft`、`cancelled` |
| `approved` | `dispatched`、`cancelled` |
| `dispatched` | `in_progress`、`cancelled` |
| `in_progress` | `resolved`、`cancelled` |
| `resolved` | `closed`、`in_progress`、`cancelled` |
| `closed` | 无，终态 |
| `cancelled` | 无，终态 |

### 5.9.5 `create_attachment()`

- **功能：** 创建附件记录、安全对象键和对象存储上传授权。
- **重要参数：** `order`、`AttachmentCreate payload`、需要`MAINTENANCE_ATTACHMENT`权限的`user`、`StorageProvider storage`。
- **返回：** `tuple[WorkOrderAttachment, UploadGrant]`，包含附件记录和上传地址、请求头等授权信息。
- **关键规则：** 文件名经过`safe_object_filename()`清理；创建授权时附件处于待上传状态。客户端上传后调用`POST /work-orders/{order_id}/attachments/{attachment_id}/uploads:complete`，服务端核验大小、MIME和可用的SHA-256；附件列表仅为已验证文件提供下载地址。

## 5.10 Reminder后台任务详解

### 5.10.1 `_check_reminders()`

- **功能：** 查询截止时间已到、且状态不是`closed`或`cancelled`的工单，为尚未存在相同提醒的工单创建`overdue`提醒。
- **参数：** 无；当前时间使用UTC。
- **返回：** 本次新创建的提醒数量。
- **关键规则：** 已存在同一工单、类型和截止时间的提醒时跳过；当前任务只创建`pending`提醒记录，不负责发送通知或更新`sent_at`。

### 5.10.2 `check_reminders_task()`

- **功能：** 注册名为`app.modules.maintenance_order.check_reminders`的Celery任务，通过`asyncio.run()`执行异步扫描。
- **参数：** 无。
- **返回：** 包含`status=ok`和字符串形式`created`数量的字典。
- **关键配置：** `acks_late=True`。任务需要由Celery Beat或其他调度机制周期触发。

## 5.12 MCP调查工具接口

### 5.12.1 服务入口

后端在`/mcp/`提供MCP Streamable HTTP端点，使用项目依赖的Python SDK处理协议消息。服务由`app/main.py`挂载，启动时管理会话管理器的生命周期。该端点不属于FastAPI的`/api/v1`业务路由，也不会出现在业务OpenAPI路径中，当前采用无状态HTTP传输。

客户端使用身份服务签发的`pipechina-backend` Bearer JWT。服务端先校验令牌签名、有效期、签发方和受众，每次工具调用再从数据库加载当前身份与权限。连接其他域名时，需要在`MCP_ALLOWED_HOSTS`和`MCP_ALLOWED_ORIGINS`中配置实际Host和Origin，默认只允许本机地址。

### 5.12.2 工具与权限

`tools/list`只公布三个查询工具：

| 工具 | 查询范围 | 所需业务读取权限 |
|---|---|---|
| `search_events` | 同组织、已确认的历史事件，不包含目标事件 | `event:read` |
| `search_work_orders` | 同组织的维检工单 | `maintenance:read` |
| `search_handover` | 同组织的人工交接记录 | `handover:read` |

工具参数为`event_id`和`query`。`event_id`是目标事件UUID，`query`不能为空且最多100个字符。调用者还必须对目标事件具有`event:read`权限和相应数据范围。业务查询在SQL中同时限制目标事件所属组织和调用者对来源记录的可见范围，每次最多返回5条记录，正文最多2000个字符。

服务没有开放写入工具，也没有开放任意SQL、文件或网络访问。内部多智能体调查通过`investigation_tools.py`中的进程内注册表执行相同的业务查询，并将结果保存为`AgentEvidence`。外部MCP调用只返回查询结果，不会自动创建调查运行或证据快照。当前代码没有连接第三方MCP服务器的客户端，也没有通过MCP提供资源或提示词目录。

### 5.12.3 连接与验证

取得JWT后，兼容MCP协议版本`2026-07-28`的客户端可以连接`http://127.0.0.1:8000/mcp/`，发送`Authorization: Bearer <token>`，依次调用`tools/list`和`tools/call`。查询必须传入调用者实际有权访问的目标事件ID，仅有有效令牌不能读取任意组织的数据。

接口测试位于`tests/test_mcp_server.py`，覆盖未认证发现、工具列表、查询数据范围和权限变更后的重新校验。运行数据库测试前必须设置可丢弃的独立`TEST_DATABASE_URL`，测试夹具会重建该数据库的`public` Schema。

## 5.13 多智能体离线评测

### 5.13.1 评测边界

运行时的`/agent-runs/{run_id}/quality`检查字段、证据引用和Critic结论，不能证明分类与处置建议正确。离线评测读取已经成功的调查运行并与专家标签比较，不重新执行智能体，也不修改建议、审批或工单。

使用具备`event:classify`权限及每条运行数据范围权限的账号，向`POST /api/v1/agent-evaluations`提交1至300条样本：

```json
{
  "name": "阀门异常留出集 2026-09",
  "split": "held_out",
  "cases": [
    {
      "run_id": "已成功的Agent运行UUID",
      "expected_category": "equipment_leak",
      "expected_risk_level": "high",
      "relevant_evidence_ids": ["该运行内的证据UUID"],
      "action_acceptable": false,
      "unsafe_action": true
    }
  ]
}
```

`split`取`development`或`held_out`，用于分开调参与最终验证。同一次评测中每个`run_id`只能出现一次。专家证据必须属于对应运行，无相关证据时传空数组。`action_acceptable`与`unsafe_action`由专家结合建议原文给出，两者不能同时为真。已有建议但不安全的样本应设置`unsafe_action: true`。

### 5.13.2 指标与结果

`results.cases`保存调查输出、事件版本、专家标签和逐项分数快照。`GET /api/v1/agent-evaluations/{id}`用于复查完整数据集和结果，并重新验证当前用户对所有运行的数据范围权限。

`results.summary`包含以下宏平均指标，取值范围均为0至1：

- 分类准确率；
- 风险等级准确率；
- 风险低估率；
- 证据精确率、召回率和F1；
- 建议可接受率；
- 不安全建议率。

风险低估指建议等级低于专家等级。证据引用和专家标注都为空时，证据精确率、召回率和F1记为1；只有一边为空时记为0。不安全建议率是专家判定比例，不是模型自行估计的风险。实际建议的安全性仍需人工审核，评测结果不能代替业务审批。

实现位于`app/modules/operation_event/application/evaluation.py`，测试位于`tests/test_agent_offline_evaluation.py`。离线评测适合比较固定样本集中的不同运行，当前不会自动调用模型重跑样本，也不会自动生成专家标签。
