# 第 5 章 异常分级与维检工单模块开发

## 5.1 本章目标

本章实现异常分类候选、人工审核和维检工单状态机。核心安全原则是：

> 模型可以提出分类、风险等级和建议，但不能自动批准高风险业务动作，也不能直接创建、派发或关闭工单。

完整流程：

```text
已确认生产事件
  -> 千问生成异常分类候选
  -> 保存 AbnormalityAssessment
  -> 创建 WorkflowRun，等待人工审核
  -> 审核驳回：流程结束
  -> 审核通过：确定性代码创建草稿工单
  -> 工单复核、批准、派发、执行、解决、关闭
```

## 5.3 设计数据模型

| 实体 | 用途 |
|---|---|
| `AbnormalityAssessment` | 保存模型分类、风险等级、理由、建议及人工审核结果 |
| `WorkflowRun` | 保存审核流程状态、当前节点和状态快照 |
| `WorkOrder` | 工单主记录与乐观锁版本号 |
| `WorkOrderTransition` | 每次状态转换的不可变时间线 |
| `WorkOrderAttachment` | 工单附件对象键和元数据 |
| `WorkOrderReminder` | 到期、超时等提醒计划 |

工单主记录：

```python
class WorkOrder(UUIDPrimaryKeyMixin, TimestampMixin, Base):
    __tablename__ = "work_orders"

    organization_unit_id: Mapped[UUID]
    event_id: Mapped[UUID]
    source_workflow_run_id: Mapped[UUID]
    order_no: Mapped[str]
    title: Mapped[str]
    description: Mapped[str]
    risk_level: Mapped[str]
    status: Mapped[str]
    version: Mapped[int]
    assignee_id: Mapped[UUID | None]
    due_at: Mapped[datetime | None]
    created_by: Mapped[UUID]
```

`source_workflow_run_id` 建立唯一约束，保证同一次审核通过最多创建一张工单。

## 5.4 理解 LangGraph 的使用边界

LangGraph 用于表达流程节点和条件路由，不代替数据库状态机，也不代替权限检查。

本模块的图只处理已经由人工提交的审核决定：

```python
class MaintenanceState(TypedDict, total=False):
    approved: bool
    review_reason: str
    decision: str


def route_review(state: MaintenanceState) -> str:
    return "approved" if state.get("approved") else "rejected"
```

图结构：

```text
START
  -> route_review
      -> approved -> END
      -> rejected -> END
```

数据库中的 `WorkflowRun` 才是可审计、可查询、可恢复的业务状态。图执行结果必须写回数据库。

## 5.5 建立审核接口

审核请求：

```python
class ReviewInput(BaseModel):
    approved: bool
    reason: str = Field(min_length=2, max_length=1000)
    expected_version: int | None = None
```

`POST /workflows/{workflow_id}:review` 顺序如下：

1. 加载 WorkflowRun；
2. 校验组织数据范围；
3. 校验状态必须为 `awaiting_review`；
4. 加载 AbnormalityAssessment；
5. 执行 LangGraph 条件路由；
6. 保存审核人、原因和状态快照；
7. 驳回时结束流程；
8. 通过时检查是否已有对应工单；
9. 创建 `draft` 工单和第一条 Transition；
10. 提交审计日志。

通过路径中的工单描述由事件当前版本和人工审核通过的建议组成。模型不能绕过审核接口直接调用工单创建函数。

## 5.6 定义工单状态机

```python
ALLOWED_TRANSITIONS: dict[str, set[str]] = {
    "draft": {"pending_review", "cancelled"},
    "pending_review": {"approved", "draft", "cancelled"},
    "approved": {"dispatched", "cancelled"},
    "dispatched": {"in_progress", "cancelled"},
    "in_progress": {"resolved", "cancelled"},
    "resolved": {"closed", "in_progress", "cancelled"},
    "closed": set(),
    "cancelled": set(),
}
```

状态含义：

| 状态 | 含义 |
|---|---|
| `draft` | 审核通过后形成的草稿 |
| `pending_review` | 工单内容等待审批 |
| `approved` | 工单审批通过，尚未派发 |
| `dispatched` | 已指定执行人和期限 |
| `in_progress` | 现场处理中 |
| `resolved` | 执行人提交解决结果 |
| `closed` | 复核后关闭 |
| `cancelled` | 有原因地终止 |

状态转换只能由应用 Service 执行，不能直接在 Router 中修改 `status`。

## 5.7 实现乐观锁

每次转换请求携带 `expected_version`：

```python
if order.version != expected_version:
    raise ConflictError(
        "work order version mismatch",
        expected=expected_version,
        actual=order.version,
    )
```

转换成功后：

1. 更新状态；
2. `version += 1`；
3. 创建 `WorkOrderTransition`；
4. 保存操作人、原因、时间和转换后版本；
5. 写入审计日志；
6. 提交事务。

乐观锁用于阻止两个用户基于同一旧版本同时派发或关闭工单。

## 5.8 实现工单复核

`draft -> pending_review` 由提交复核接口完成。`pending_review` 的审核结果：

- 通过：`pending_review -> approved`；
- 退回：`pending_review -> draft`；
- 取消：`pending_review -> cancelled`。

审核请求必须包含原因。审批权限和普通状态转换权限分开配置。

## 5.9 实现派发与执行

派发接口输入：

```python
class DispatchInput(BaseModel):
    assignee_id: UUID
    due_at: datetime
```

派发只能从 `approved` 进入 `dispatched`。后续执行顺序：

```text
dispatched -> in_progress -> resolved -> closed
```

`resolved` 可以退回 `in_progress`，用于复核不通过的情况。`closed` 和 `cancelled` 都是终态。

## 5.10 建立附件上传

附件仍使用 `StorageProvider`，不能在 Service 中直接操作本地路径：

```python
attachment.object_key = (
    f"work-orders/{order.id}/{attachment.id}/{safe_object_filename(payload.filename)}"
)
grant = await storage.create_upload(
    object_key=attachment.object_key,
    mime_type=payload.mime_type,
    size_bytes=payload.size_bytes,
)
```

附件上传应增加完成校验接口或复用平台上传会话，确保数据库记录不指向未上传对象。

## 5.11 建立提醒任务

`WorkOrderReminder` 保存：

- `reminder_type`；
- `scheduled_at`；
- `status`；
- `sent_at`；
- `payload`。

Celery Beat 每分钟执行 `check_reminders`，查询到期且 `pending` 的提醒，投递通知后更新状态。通知渠道属于独立端口，不应直接写死在任务函数中。

## 5.14 编写测试

核心测试矩阵：

| 场景 | 预期 |
|---|---|
| 审核通过 | 创建一张 draft 工单 |
| 同一工作流重复审核 | 不重复创建工单或返回冲突 |

| 旧 expected_version | 返回 409 |
| 合法完整链路 | draft 到 closed 全部有时间线 |
| resolved 退回 | 返回 in_progress，版本递增 |
